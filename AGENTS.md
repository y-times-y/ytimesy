# ytimesy

Never invent a Git identity or impersonate a person, including Het. Managed agent commits use `ytimesy-agent[bot] <328807657+ytimesy-agent[bot]@users.noreply.github.com>` as both author and committer and include the same identity in a `Co-authored-by` trailer. Do not change Git identity in user-owned local repositories. If the authorized identity cannot be verified, stop rather than guessing.

Before implementation or architectural changes, read [PLAN.md](PLAN.md) for the product scope, accepted stack, module boundaries, and acceptance criteria.

Before writing or reviewing code, apply [.agents/skills/self-documenting-code/SKILL.md](.agents/skills/self-documenting-code/SKILL.md). Keep routes thin, models focused, and provider details behind explicit adapters.

Reuse before building: before implementing general-purpose logic, inspect existing project utilities, platform APIs, and maintained libraries that solve it. Verify compatibility, security, maintenance, licensing, and the actual user workflow before choosing. Prefer the smallest suitable existing solution; keep custom code focused on product-specific behavior. If custom logic is necessary, explain the concrete gap first. When replacing custom logic with a library, remove the superseded implementation and test the integration, including edge cases and live behavior.

Frontend: before building or changing any server-rendered UI that depends on client-only state (localStorage choices, the clock, screen size, media queries, typed input), apply [.agents/skills/no-snap-first-paint/SKILL.md](.agents/skills/no-snap-first-paint/SKILL.md). The first paint must already be correct: nothing may snap or flicker when React hydrates, and there must be no hydration mismatch.

Use agent-browser for browser research and UI verification, as requested by the user. Keep reference screenshots out of commits. Report live verification separately from mock tests and build checks.

The first release must include Diff, Terminal, and Desktop. ytimesy runs only its own harness (the model loop in `src/server/jobs/api-turn.ts`), with two model sources: `codex` (the user's ChatGPT subscription, signed in from the web server in `src/server/auth/codex-device-login.ts`) and `api` (the user's API connections). No other third-party agent CLI (Codex CLI, OpenCode) runs in workspace VMs. The exception is Claude Code: a chat on a Claude subscription runs `claude` on its own VM with its built-in tools, and the user's token stays on the edge (`src/server/services/claude-code-runner.ts`). Before proposing to move it off the chat VM, read [Where Claude Code runs](docs/claude-code-placement.md): a separate runner pool was considered and turned down, and that doc records why and what it costs. Freestyle, TanStack Start, and Effect are selected. Consult PLAN.md for unresolved provider choices rather than silently treating proposals as decisions.

Before database schema changes, Supabase setup, or migration deployment, read [Supabase and GitHub workflow](PLAN.md#supabase-and-github-workflow). It records the selected provider, migration ownership, integration settings, and unverified setup state.

Workspace VM lifecycle: idle chat VMs pause after 180 s and Freestyle deletes them after 90 days without running. Recycling (snapshot the VM, delete it, restore a new one) was stopped on 2026-11-11 because it saves no storage and returns slower; read the decision at the top of [Workspace retention](docs/workspace-retention.md) before proposing snapshots as a cost saving.

Cloudflare execution: there are no Workflows. Before adding one, moving work into a Durable Object alarm or cron, or changing how chat turns or environment builds run or resume, read [Cloudflare execution model](docs/edge-architecture-migration.md#cloudflare-execution-model-decision-2026-10-12). Alarms and cron stop after 15 minutes, and Durable Objects restart on every deploy.

Bookkeeping never blocks the user: usage accounting, analytics, logging, alerts and other records about an action must not fail the action itself (starting a VM, sending a message, saving work). When their numbers disagree or their write fails, log it (and alert if it repeats) and let the action through. A usage-settlement mismatch once refused to wake a chat's VM forever (`settleHold`, 2026-11-04), and a crash-looping log source once used most of the log quota.

Production deploys: run only `node --import tsx scripts/deploy-production-from-secret.ts --confirm-production` from a checkout of current `origin/main`. Never hand-roll `vite build` plus `wrangler deploy`: on 2026-11-12 a deploy from an unpushed commit that lacked main replaced a shipped UI fix. The production web build itself (`vite.config.ts`) now refuses a checkout that does not contain `origin/main`; `YTIMESY_ALLOW_UNVERIFIED_SOURCE=1` overrides it only for a deliberate hotfix the user approved.

Infrastructure as code: Workers, their bindings and secrets, and the AWS turn box fleet are Alchemy stacks in `infra/alchemy` (its own package, so its two patches and lockfile stay apart; the app and the stacks are both on Effect 4). Change infrastructure only with `node --import tsx scripts/infra.ts plan|deploy <cloudflare|aws> --stage <development|production>`, never `alchemy deploy`, `wrangler deploy` or the AWS console. Run `plan` first and report it. Never remove `RemovalPolicy.protect()`, rename a logical id or pass `--adopt-existing` without the user's go: it refuses deletions and replacements on purpose. Read [Infrastructure as code](docs/infrastructure-as-code.md) first; it has the rollout state and the two local Alchemy patches an upgrade must keep.

Deploys and open tabs: a tab keeps running the old page until it reloads onto the new build (`src/features/app/new-build-reload.ts`), so for one deploy it calls the new server with the old client. When you change a server function's or API route's input shape, accept both the old and the new shape for one deploy, and drop the old one in a later deploy.

Public harness: this monorepo is the public one. The separate `y-times-y/harness` repo is private and is not maintained; do not port changes to it, publish it, or flag it in reports. `packages/ytimesy-cli` is the source of the published `ytimesy` package, and the product's hand-off prompt runs `npx -y ytimesy@latest`, so a CLI change reaches live users on the next npm publish: bump the version, run a plan-only hand-off first, and leave the publish to the user. Never copy product-only code (Freestyle, Cloudflare, the database, billing, secrets) into anything published.

Before starting or changing any benchmark run, read [docs/benchmark-lessons.md](docs/benchmark-lessons.md): its checklist exists because each item cost real GPU hours or results.

Before proposing or running any harness or benchmark experiment (A/B, variant comparison, replay), search [docs/research/experiment-log.md](docs/research/experiment-log.md), then `docs/research/` and `git log` for the same hypothesis. If it was already tested, report the earlier result instead of rerunning; rerun only for a stated reason (the code changed, the earlier sample was too small). After any experiment, add one line to the log, including small and failed ones.
