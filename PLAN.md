# ytimesy v0

Status: harness architecture updated on 2026-09-30. ytimesy owns recursive task orchestration; Codex and Claude Code are its offered runtime adapters. OpenCode references in dated evidence below are historical and do not authorize new OpenCode sessions. Writers use snapshot-copy isolation; read-only child tasks share their parent's machine with session-scoped runtime state. Codex runs on an isolated per-user server-side runner with per-chat native state and server-managed subscription access tokens; execution VMs remain separate. Private Supabase Storage is selected for encrypted recovery checkpoints; frontend hosting remains undecided. Domain: ytimesy.com. Updated: 2026-09-30.

## Goal and proof

Build a hosted interface for using a user's coding agent on their GitHub repositories. Users operate projects and agent sessions; ytimesy provisions and manages their cloud environments. The first user is Het, but authorization and records must support multiple isolated users from the beginning.

V0 is complete when Het connects a real private repository and his own agent access, completes a task, inspects the diff, uses the terminal and the shared desktop, closes the browser without interrupting active work, reconnects, and explicitly publishes a commit and PR. A rendered UI or successful build alone does not satisfy this goal.

## Product scope

1. Sign in; install a GitHub App with selected-repository access.
2. Choose a repository and branch. Prepare a project environment snapshot (dependencies, project configuration, and necessary credentials). Each agent session then gets its own Freestyle VM copied from that snapshot.
3. ytimesy provides the harness. Codex and Claude Code are runtime adapters beneath it; OpenCode is retained only for existing sessions and is not offered for new work. The composer defaults to Codex. Users select models listed by the connected runtime. Subscription sign-in and bring-your-own API key are both options; stored keys are encrypted at rest (AES-256-GCM) and never returned in plaintext. Do not silently fall back to paid inference. Claude Code must stay unmodified; do not offer Claude.ai login inside ytimesy, intermediate Anthropic billing, or use Anthropic marks as ytimesy branding. Never invent model names.
4. Start and steer an agent session. Show messages, tool activity, progress, approvals, cancellation, and actionable failures.
5. Inspect that session's workspace through Files, Diff, Terminal, and Desktop. Files is a tree of this chat's working-tree edits; clicking a file the agent mentioned opens that file with red/green diff coloring. Desktop is a shared Linux display the agent can computer-use and the user can watch and control. App preview is a window on that desktop, not a separate Tools tab. The terminal is explicitly required in v0.
6. Continue active work independently of the web application request or browser connection. Reconnect to retained sessions; expose expired authentication and recovery states clearly.
7. Automatically commit changed files in isolated writable chats when a turn completes successfully, before completed status and review events become visible. Skip clean trees, shared/read-only tasks, failed turns, and unfinished Git conflicts or rebases. Repeated completion observations must not commit a later turn's edits. Keep push and create-PR actions explicit; do not silently publish or fall back to paid API inference. Task review diffs include commits since the checkout's saved base, which is retained in recovery checkpoints.

Workspace isolation: a Project owns a prepared environment (Rigkit apply / clone-and-install, then a Freestyle snapshot or a warm spare that agents never edit). Every writer owns a distinct Freestyle VM copied from the template (`vms.create({ snapshotId })` or `vm.fork()` of the unused warm spare). Competing writers run in parallel with separate working trees, indexes, ports, PTYs, and previews. Read-only child tasks instead share the parent machine and exact working tree; session-scoped runtime files and provider read-only modes keep their conversations separate. Reconnect pauses/resumes the same machine identity. Each writer checkout uses its own branch for publication.

Project context is an agent-context concern, not a VM concern and not a Codex-only concern. Root threads under the same Project may receive a durable briefing plus selected reasoning traces across runtime adapters. Child tasks are different: they start from their standalone task prompt alone and never receive the parent transcript, automatic sibling traces, or an implicit briefing. After a root session, keep selected traces and a short briefing update; do not require another root agent to replay the full transcript. Resume continues one session; forking a conversation is explicit.

Lead-agent policy is owned by ytimesy and injected through every runtime adapter. New root conversations are read-only leads: they may inspect, plan, coordinate, and answer simple questions, but a requested code change requires at least one fresh read-write Build child. Build children can implement their own bounded tasks directly and may delegate further when useful. Every task records a standalone prompt, runtime/model, read-only or read-write access, shared or fresh placement, parallel or stacked execution, and any stacked predecessor. Additional delegation is for bounded work where parallelism, specialization, or an adversarial pass materially improves the outcome. The lead chooses the smallest coherent task count; recursion is capped at three levels and provider capacity remains an infrastructure limit. Child prompts must be self-contained. Leads continue useful read-only investigation while children run, check status without tight polling, steer drift, and request wrap-up rather than waiting indefinitely. Completion and blocked questions enter a durable outbox that wakes an idle parent. Leads inspect and explicitly review child diffs before publication. Stacked work starts only after the predecessor is reviewed and published, from that pull-request branch rather than a VM snapshot.

API-key model loops run in the durable server worker and call VM-backed tools. Codex subscription now uses the isolated server-side runner described below, with execution bound to a per-session VM and subscription billing preserved. Durable conversation state and task coordination remain server-owned.

Peer coordination: `list_peers` exposes bounded objectives and status within the current owner/project/task tree; `send_peer_message` sends findings, duplicate-work handoffs, and file-ownership negotiations directly between agents. Each competing candidate subtree is a separate coordination group. Peer messages do not grant edit, start, review, or publication authority over another task, and no transcripts are automatically broadcast. The existing pg-boss worker retains each message until runtime acknowledgement, with 15-second retries over a bounded window (approximately 24 hours). Active Codex turns use native `turn/steer` with the expected turn ID; API runs checkpoint peer input at the next model-step boundary, before context compaction and budget checks; unmodified Claude Code receives context through UserPromptSubmit, PostToolUse, PostToolUseFailure and Stop hooks. Per-message mailbox files avoid overwrite, shared-task paths are session-scoped, and API/Claude consumers filter recipient identity so snapshot copies cannot inherit another task's pending messages. A finished-turn race falls back to the recipient's own runtime/model as a follow-up. Old active daemons are not restarted to install steering; they finish safely before upgrade. Delivery does not cancel commands, replay work, or modify already-streamed tokens. This is not a file lock or a transactional exactly-once inference guarantee: a crash between native acceptance and receipt persistence can still require transcript-based recovery. Fresh writer machines still need reviewed integration or stacked dependencies to share actual edits. Earlier bounded subscription-backed tests proved sibling discovery, native send_peer_message calls and deferred receipt. Automated coverage now also checks native steering acceptance/rejection, Claude hook context, recipient filtering, API checkpoint-before-acknowledgement and preservation across successive model steps. The protocol mechanisms are documented in the [Codex app-server reference](https://developers.openai.com/codex/app-server#steer-an-active-turn) and [Claude Code hooks reference](https://code.claude.com/docs/en/hooks). Live Claude/API peer coordination and autonomous multi-writer conflict negotiation are not established by the read-only Codex tests.

Historical routing proofs on 2026-09-28 established subscription-backed remote reads and provider-enforced read-only writes using Codex 0.157.1 and an executor initially running 0.147.0. A disconnected executor nevertheless returned a completed text-only turn, motivating independent health checks. An attempted Docker-container cutover on the privileged job worker failed because the container could not reach the restricted TLS route; host networking would have exposed worker-local services, and kernel firewall isolation was unavailable. That approach was removed. The active solution instead separates the credential-limited per-user runner from the privileged worker, adds encrypted recovery checkpoints and brokers Git authority on the server. The sections below record current implementation and bounded live evidence; no environment connection probe alone proves execution isolation or production readiness.

Remote-executor failure handling was live-tested on 2026-09-30 with Codex 0.157.1 on two disposable Freestyle VMs using subscription authentication. The adapter completed a normal remote read, then failed a deliberately disconnected turn in 0.71 seconds and stopped the harness process to prevent delayed continuation. It consumes the native `thread/environment/disconnected` notification, scoped to the active thread and environment. Health checks use fail-fast `environment/status`, not the recovering `environment/info` call; the latter is reserved for initial connection. For silent failures, status RPCs are multiplexed through the existing protocol reader every second with a two-second response deadline. Application tool handling and token refresh do not count against that deadline. This replaces the earlier polling-only test's 6.9-second detection. Both test VMs and their source-restricted TLS rule were deleted. Forty-four targeted Codex tests passed. This verifies the adapter's tested failure boundary, not a deployed server-hosted cutover or coverage of every tool path.

### Recovery checkpoints and Git authority — 2026-09-30

Settled turns enqueue encrypted off-machine checkpoints in a private Supabase Storage bucket. A durable minute sweep backstops missed enqueue operations, with bounded batches, singleton per-chat jobs and retries. Captures preserve Git commits, shallow boundaries, staged/unstaged changes, untracked non-ignored files, and allowlisted per-chat Codex rollouts, thread state and SQLite state. Native auth files and ignored dependency directories are not included. The existing server-side token vault encrypts owner-bound payloads before upload; both metadata lookup and decryption enforce ownership. Storage credentials remain on the trusted control plane. Backups are limited to 20 MiB of plaintext; this is last-settled-turn recovery, not continuous disk replication. UI reads never wake machines; background capture explicitly resumes an existing executor and Codex runner only when their conversation needs a new backup.

Missing execution VMs restore owned saved work into a replacement project-template copy before binding it to a conversation. Missing Codex runners restore their chat-scoped native history and rebind only to the recorded executor. No saved checkpoint means fail closed, not replay or silently discard edits. Template dependencies remain prepared; ignored local files, private Git LFS blobs, and submodule work are not covered by the current Git checkpoint format.

Git clone, clean refresh, stacked-task fetch and publication now use a trusted Git bundle broker. Repository-scoped installation tokens are minted only on the server. The guest receives credential-free Git objects and a normal HTTPS origin, not a token or authenticated remote. The broker uses fresh bare repositories, disabled hooks, restricted protocols, object verification and a 64 MiB bundle limit. Dirty refreshes leave local work untouched; pushes are explicit and non-force. Publication fetches base history on the broker so existing shallow checkouts can publish without exposing credentials. This does not claim that parsing untrusted Git objects is equivalent to an OS sandbox, or that private LFS/submodule authentication is implemented.

Development evidence: the private bucket was created and the additive checkpoint migration applied. Real encrypted upload/download passed and cross-owner reads were blocked. A live server-authenticated repository clone left no GitHub token in the guest. An existing settled conversation's live checkpoint restored one repository and four native Codex history files into a separate verification directory, with credentials excluded. Real local Git tests cover staged/unstaged/untracked restoration, shallow restoration, credential-free clone/push and dirty refresh preservation. Recovery orchestration tests require restore-before-bind and reject failed restores.

The disposable daily-flow drill then deleted a real builder execution VM and removed only that chat's native runner directory after capturing its checkpoint. Sending to the same chat created a replacement executor, restored both untracked implementation files, preserved the exact native thread ID, and reran the existing Node test successfully without recreating files. The shared runner VM itself was retained to protect sibling chats: physical loss and replacement of that entire host is not separately live-tested. Existing user VMs and chats were preserved.

### Isolated Codex runner integration — 2026-09-30

The active adapter now provisions one reusable, owner-verified Freestyle runner per user, separate from the privileged job worker and from execution workspaces. Each chat has its own durable HOME, CODEX_HOME, protocol daemon, and saved native thread. CLI versions are pinned centrally in `src/domain/guest-cli-pin.ts`; the native daemon fingerprint includes the Codex pin so an idle session reloads its model catalog after a deliberate upgrade. Active turns defer that restart. The runner receives short-lived access tokens, never the database, GitHub, Freestyle, or subscription refresh credentials. The encrypted server-side credential broker owns refresh rotation. A source-restricted internal TLS route connects the runner to the chat's execution VM; Files, Diff, Terminal, Desktop, environment preparation, and builder placement continue to use that execution VM.

Reads do not provision or wake an idle runner. Send wakes both machines, prepares the executor, restores the native thread, then starts the turn. Active reconciliation keeps both machines awake; otherwise the runner suspends after 180 seconds of network idleness. One user runner serves multiple chats, with OS file locks serializing shared CLI installation and executor startup. Ownership or executor-binding mismatches fail closed. A migrated chat whose runner disappears must restore native history rather than replay the old execution-side transcript. Retained disk supports ordinary process/VM restart; it is not an off-machine backup. Freestyle plan retention still applies even when no application deletion deadline is requested.

The app's refresh reconciliation, streaming watcher, dynamic task-tool bridge, Stop, and chat deletion now resolve the same native runner capability. Shared-child streaming resolves its child-scoped executor binding rather than accidentally reading the parent's binding. Deleting a chat removes its native state without deleting the shared runner or sibling chats. Existing inactive native histories migrate only their own rollouts, not credentials. Startup no longer adds an artificial eight-second poll delay. A cold executor can reconnect before turn/start; once a turn is dispatched, disconnection still fails fast without automatic replay. Native cancellation includes both threadId and turnId, including Stop before the start acknowledgement; see the [app-server interrupt contract](https://developers.openai.com/codex/app-server#interrupt-a-turn).

Live evidence through the production adapter: subscription authentication and model discovery; shell reading a marker only on the execution VM; apply_patch writing only on that VM; view_image opening an executor-only red PNG and identifying its color; a remote read-only shell write rejected with Read-only file system and no created file; app-server restart followed by a turn remembering prior context; cancellation returning the native interrupted result with no remaining test sleep process; a simulated native refresh request causing real broker token rotation without exposing the refresh token; and an authenticated browser chat showing remote shell activity and its final response. A fresh lead also created and started a shared read-only child, received its package script lookup, inspected the empty diff, and marked the result reviewed. The first child attempt exposed a cold-connection failure and passed on retry; the second fresh child completed without retry after preflight reconnect was added. A comparison-judge rejection exposed a task-tool defect that previously expired its receipt rather than returning an error; the tool boundary now completes error responses for both typed failures and thrown validation errors. An older native chat had no registered task tools in either source or destination state: its history was preserved, but a new chat was used to verify the current toolset. Older tool-registration metadata migration is not separately verified. These are bounded integration proofs, not a claim that every tool or production load level is verified. The recovery and daily-flow sections above record the later destructive executor-loss, encrypted history restoration and Git broker proofs.

Environment speed is separate from context. A new agent VM is a copy of an already-prepared project snapshot (`vm.fork()` or `vms.create({ snapshotId })`), so opening another agent does not run setup. The first project setup must still be fast: boot a prebaked tools image (Node, git, Codex CLI, Claude Code CLI, package store — no user secrets), then clone and install with warm caches, and snapshot immediately. Codex login is not copied into either project or execution images; the control plane supplies short-lived access tokens to Codex workers. Claude Code's separate auth-image path remains pending its own live validation. Do not install OS tooling per project, do not copy Cursor hourly Builds as the user-visible wait, and do not block a second agent on `pnpm install`. Composer can bind as soon as that session's VM is reachable.

Do not put two writers in one checkout, use git worktrees to fake write isolation, serialize competing writers on a shared VM, or re-run `pnpm install` when opening a new agent. Read-only audit tasks may share the parent's machine only through session-scoped runtime state and provider-enforced read-only permissions.

Later: local session import/handoff, additional runtime adapters, non-Git folders, fresh project/repository creation, advanced collaboration, automations, and billing UI. Preserve clean extension boundaries without implementing speculative features.

## Supabase and GitHub workflow

Decision recorded 2026-09-13: use Supabase PostgreSQL on the Free plan initially. Better Auth remains the application authentication system. Access PostgreSQL from server-side modules through `DATABASE_URL`; Supabase Auth and the Data API are not required by this architecture.

### Integration settings

The intended Supabase GitHub integration configuration is:

| Setting | Value |
| --- | --- |
| Repository | `y-times-y/ytimesy` |
| Working directory | `.` (parent of the root `supabase/` directory) |
| Production branch | `master` |
| Automatic branching | Off initially; preview databases have separate pricing/plan requirements |

This integration manages database changes from this repository. It is separate from the ytimesy GitHub App that grants users access to their coding repositories. Linking the repository alone is not authorization to enable automatic production deployment.

### Migration ownership

Initialize and commit `supabase/config.toml` and ordered SQL files under `supabase/migrations/` when implementing the database. The CLI configuration is initialized. Migrations `20260913010000_enable_automatic_rls.sql` and `20260913193000_identity_and_projects.sql` are applied. The latter contains Better Auth, encrypted GitHub connections, single-use OAuth state, and personal project records. Capture any existing application schema before introducing migrations; inspect the actual database rather than assuming it is empty. Treat migrations as the authoritative schema history, including Better Auth tables and job-system setup. pg-boss creates and migrates its own tables inside the `job_queue` schema at process start; application migrations only create that schema and revoke Data API access. Do not copy pg-boss DDL into `supabase/migrations/`. Account for libraries that create or migrate their own schemas so two independent mechanisms do not race or diverge.

For a schema change, add a new migration, verify it against a disposable development database, and review it with the application changes. Preserve already-applied migrations. Keep production data and credentials out of migration/seed files. Preview branches rebuild schema from committed migrations and optional seeds; they do not automatically copy production schema or data.

Before enabling automatic production deployment, validate clean schema creation and upgrades from the preceding schema, establish a required migration check in GitHub, and document recovery for failed migrations. Supabase's production deployment option applies new migrations and configured functions/storage buckets when commits reach the configured production branch. Treat enabling it as a separate deployment decision.

## Modules and dependency direction

Read and apply [.agents/skills/self-documenting-code/SKILL.md](.agents/skills/self-documenting-code/SKILL.md), installed from theswerd/aicode, before implementing or reviewing code.

Start with one repository and independently runnable web/worker entry points when workers exist. Modularize by responsibility, not by making every function a package. Create modules as their first working flow is implemented:

- `src/routes`: navigation, request validation, authentication boundary, composition; no provisioning logic.
- `src/features/projects`: repository selection and project UI.
- `src/features/sessions`: conversation, activity, composer, session controls.
- `src/features/workspace`: panel layout, changes, terminal, desktop.
- `src/components/ui`: shared visual primitives with no infrastructure knowledge.
- `src/domain`: precise models, branded IDs, valid state transitions, pure policies.
- `src/server/services`: Effect workflows for project setup, session lifecycle, publication, and recovery.
- `src/server/adapters`: Freestyle, Rigkit, GitHub, agent protocol, database, and job implementations. Keep provider-specific details here.
- `src/server/auth`: identity, tenant membership, repository permissions, provider-connection boundaries.
- `src/server/jobs`: durable job handlers and reconciliation, independent of request lifetime.

Dependency flow: UI → authenticated server entry → service → defined capability → adapter. Domain logic does not depend on React, HTTP, or provider SDKs. Server-only modules and credentials must not enter browser bundles. Boundary inputs are validated at runtime; external strings do not become trusted IDs merely through a cast.

### Review rules

- Small semantic functions take required inputs and return explicit outputs. Side effects are explicit responsibilities.
- Workflow functions compose steps; document non-obvious behavior such as retries, recovery, and publication boundaries.
- Model independent concepts separately. Prefer explicit state variants over unrelated optional fields.
- Distinguish UserId, ProjectId, WorkspaceId, SessionId, and JobId. A Project owns the environment template and the shared agent briefing. A Workspace is one agent VM. A Session is the conversation attached to that VM. Do not treat the briefing as VM state or collapse WorkspaceId onto ProjectId.
- Keep Effect in backend services and adapters; UI receives serializable data and actionable errors.
- Name modules for what they own. Avoid catch-all utility files, generic managers, pass-through abstraction layers, and oversized route files.
- Add an abstraction when it clarifies a real boundary, not merely to support an imagined future provider.

## Reliability and growth

Million-developer scalability is an architectural ambition, not a verified launch capacity. Registered users and concurrent VMs are different capacity measures. Establish launch concurrency targets, quotas, provider agreements, and load tests before claiming scale. Live check on this Freestyle account: create failed at **5 VMs** (`LIMIT_EXCEEDED`). Opening New chat only inserts a session row. Connect or Send on that chat copies one VM from the project snapshot until Delete chat destroys that session copy. Pausing a VM does not free a slot. Start is a different meter: this account has used its included **100 vCPU-hours**, so Freestyle refuses `vm.start` (`vcpu_time` / `memory_time`) even with free slots. Product VMs that are not copied from a larger snapshot boot `freestyle/ubuntu-sm` (2 vCPU / 4 GiB). Copies from a 4 vCPU snapshot stay 4 vCPU because resize cannot shrink. `idleTimeoutSeconds` is 180, so Freestyle pauses a VM after three minutes without public or terminal traffic. Deleting or pausing leftover VMs does not restore already-consumed vCPU-hours.

- Persist job and workspace state in PostgreSQL. A web restart must not lose ownership of work.
- Provision with idempotency and reconciliation; handle a timeout after remote creation without blindly creating a second VM.
- Limit concurrency and apply backpressure. Record infrastructure usage from the beginning.
- Preserve durable event ordering/cursors for reconnect; distinguish cached UI data from the authoritative session record.
- Effect retries and finalizers do not replace durable recovery or orphan reconciliation.
- Cancellation of a run is distinct from deleting its workspace VM. Delete chat destroys that session's VM and any side-chat copies. It must not delete the project snapshot, the template VM, or other agents' VMs. A session that was attached to the template before snapshots existed only drops the row.

A one-time device-code login is captured into that record, then removed from its execution VM. PostgreSQL row locking serializes refresh through Codex's managed app-server auth mode. Execution VMs receive only an access token and account ID through the experimental external-token app-server mode; the control plane services refresh requests. A worker must not receive the refresh token. Legacy private login snapshots are not an active product auth path. Claude Code's auth handling is separate. - GitHub authority is repository-scoped and brokered wherever practical. Untrusted repository code must not gain platform authority.
