# Capy: requesting a summary from a running agent

Checked 2026-10-06 with `agent-browser` against public first-party documentation and changelog. No authenticated agent run was performed. Published behavior below is not independent live verification.

## Documented facts

- **Delivery can happen during ongoing work.** [Threads](https://docs.capy.ai/threads) specifies three delivery modes: interrupt stops the current generation, queue waits for current work to finish, and steer inserts the message at the agent's next step without stopping work. An idle agent receives any mode immediately. The public [send-message API](https://docs.capy.ai/api-reference/messages/send-message) is `POST /api/v1/threads/{threadId}/message`; its body accepts `text`, `delivery: "queue" | "steer" | "interrupt"`, and optional `clientKey`, returning an admission receipt `{id, deduped}`. Admission is not proof that a reply already exists.
- **A run contains multiple turns.** [Streaming](https://docs.capy.ai/api-reference/streaming) defines a run as one wake comprising model generations and tool executions until the agent rests; a turn is one model generation. Live `assistant` frames carry reply fragments, and committed `transcript` entries establish the durable reply. This makes a reply during a longer run publicly representable. It does not establish concurrent context injection into an already executing generation.
- **Captain crew are threads, not child subagents.** The [changelog](https://capy.ai/changelog) describes Captain as a long-running thread directing other threads as crew. [List Captain crew](https://docs.capy.ai/api-reference/captains/list-captain-crew) returns `Thread` objects. Capy 0.4.2 says crew replies directly to the human now reach the Captain, and Captain Drive added during a running crew job arrives at its next step. These are reply routing and context-update claims; they do not disclose the Captain's messaging tool implementation.
- **Child agents have different reporting semantics.** [Subagents](https://docs.capy.ai/subagents) says children start from their prompt alone; parents receive final summaries automatically, blocked questions notify them, and ordinary interim progress does not wake the parent. The parent reads interim progress on demand. Cross-thread coordinators explicitly read sibling thread state. [Common flows](https://docs.capy.ai/api-reference/common-flows) says public subagent endpoints are read-only: an API caller changes child course by messaging the parent thread.
- **Public visibility stops at summaries.** [Streaming](https://docs.capy.ai/api-reference/streaming) and [list messages](https://docs.capy.ai/api-reference/messages/list-thread-messages) expose activity summaries and tool names, not raw tool arguments/results or internal reasoning. The model-facing Captain send/report tool names and schemas were not established by the inspected public sources. [Machines](https://docs.capy.ai/machines) places the agent loop on Capy's servers and execution on the machine; this does not identify its private mailbox or scheduler implementation.

## Inference for the described interaction

A Captain asking a busy builder to summarize and the builder answering while continuing work is consistent with: a cross-thread message delivered at a next-step boundary, the builder generating an explicit progress reply, and that reply being routed to the Captain. `steer` is the documented public delivery mode with that shape. This is an explanation supported by published semantics, not proof that Captain's private tool calls the public HTTP endpoint or uses that exact mode.

## Unknowns and observation boundary

The exact described exchange was not reproduced. The available evidence does not reveal whether Captain polls, uses timers, waits for an event, or is prompted by the human; nor its default delivery mode, private tool schema, progress-reply wake policy, busy-Captain reply timing, safe-point behavior during long tool execution, retries, or delivery guarantees. Do not infer a periodic autonomous summary request or instantaneous interruption-free response from the existence of crew messaging.
