## What memoryrepo actually implements

Memoryrepo is a standalone personal-chat web application and reference implementation of Cognition's technique. Its repository contains server and React UI code; the inspected tree has no installable Codex/Claude memory skill or startup hook. Its package is private. Calling its own HTTP chat endpoint runs its own model turn, rather than injecting memory into an existing coding runtime. [Repository tree](https://api.github.com/repos/supermemoryai/memoryrepo/git/trees/54f7ff3065df8af687dc5c04a4bb17d6611e5fd1?recursive=1), [package.json](https://github.com/supermemoryai/memoryrepo/blob/54f7ff3065df8af687dc5c04a4bb17d6611e5fd1/package.json), [chat-agent.ts](https://github.com/supermemoryai/memoryrepo/blob/54f7ff3065df8af687dc5c04a4bb17d6611e5fd1/src/server/chat-agent.ts).

The chat agent obtains the current repo snapshot before each turn, puts `MEMORY.md` into its instructions, and exposes an in-memory copy to tools. A turn allows up to twelve model steps and can stop on budget. Thus startup context injection is code-driven; deeper retrieval and memory writing depend on model tool choices. [chat-agent.ts](https://github.com/supermemoryai/memoryrepo/blob/54f7ff3065df8af687dc5c04a4bb17d6611e5fd1/src/server/chat-agent.ts).

`MEMORY.md` is a compact root/index; topic files use wiki links and single-line facts with source/date metadata. The prompt tells the model to search when earlier people/plans are relevant but absent from the root. It asks the model to save durable preferences, decisions, relationships, plans, and changes before replying, searching for existing entries first. Chat recall is `rg`/`grep` and reading linked files, not embeddings. Chat has a read-only shell and explicit write/edit/delete tools; each successful changed write commits. Dreaming has a writable vault, read-only transcript/note inbox, source lookup, and a finish tool. It may take forty steps; no finish means no resulting commit. These prompts are policy, not a semantic validator of saved facts or required metadata. [memory.ts](https://github.com/supermemoryai/memoryrepo/blob/54f7ff3065df8af687dc5c04a4bb17d6611e5fd1/src/server/memory.ts).

One MemoryAgent owns each bank's repository, serializes commits, and checks files against the writer's expected snapshot. Independent-file changes can land; changed touched files return a conflict/current contents. Dreams combine their file changes with concurrent chat changes, but conflicting file changes discard the dream without advancing cursors. The recurring schedule is four hours; a manual action also schedules a dream. The code skips an empty inbox or exhausted budget. Changed nonempty notes also populate the inbox, so a notes-only update can trigger work, despite the README's narrower “new messages” wording. Cursors advance after successful completion, including an unchanged result. The application separately implements lazy SQLite FTS5/BM25 search for wiki, messages, and notes; this search is not one of the chat model's tools. [memory-agent.ts](https://github.com/supermemoryai/memoryrepo/blob/54f7ff3065df8af687dc5c04a4bb17d6611e5fd1/src/server/memory-agent.ts).

Git storage uses Cloudflare Artifacts reads and `isomorphic-git` writes in `memfs`. It caches a working copy and write token; reuse avoids cloning for every small write. Its last-known snapshot can miss an external push until a fresh read or error invalidates it. These are implementation tradeoffs, not proof of concurrent production reliability. [vault.ts](https://github.com/supermemoryai/memoryrepo/blob/54f7ff3065df8af687dc5c04a4bb17d6611e5fd1/src/server/vault.ts), [memory-agent.ts](https://github.com/supermemoryai/memoryrepo/blob/54f7ff3065df8af687dc5c04a4bb17d6611e5fd1/src/server/memory-agent.ts).

`just-bash` operates on mounted in-memory filesystems, with mutation methods denied for read-only mounts. Commands have a twenty-second timeout and sixteen-thousand-character output cap. This is not an OS terminal over the user's machine. [shell.ts](https://github.com/supermemoryai/memoryrepo/blob/54f7ff3065df8af687dc5c04a4bb17d6611e5fd1/src/server/shell.ts).

Dependencies are substantial app infrastructure: Cloudflare Agents/AIChatAgent, Vercel AI SDK, OpenRouter adapter, Artifacts, Alchemy/Effect deployment, React/Vite, plus UI/editor/graph libraries. Runtime model resolution calls OpenRouter directly; it does not require Supermemory's hosted memory API. Usage metering prefers provider-reported cost but falls back to configured list-price arithmetic when absent, so “exact cost” is conditional. [package.json](https://github.com/supermemoryai/memoryrepo/blob/54f7ff3065df8af687dc5c04a4bb17d6611e5fd1/package.json), [alchemy.run.ts](https://github.com/supermemoryai/memoryrepo/blob/54f7ff3065df8af687dc5c04a4bb17d6611e5fd1/alchemy.run.ts), [models.ts](https://github.com/supermemoryai/memoryrepo/blob/54f7ff3065df8af687dc5c04a4bb17d6611e5fd1/src/server/models.ts).

## Cognition's actual open specification

Cognition's official [Agent Memory Repo page](https://cognition.com/agent-memory-repo) links [AgentMemoryRepo/agentmemoryrepo](https://github.com/AgentMemoryRepo/agentmemoryrepo). This is the relevant specification; the unrelated `arananet/cognition.md` project is not Cognition's standard.

The format specifies a short `MEMORY.md`, arbitrary topic layout, one-line bullet entries, open metadata keys with recommended source/date, and root-relative wiki links. The broader memory loop describes clone, retrieve, update, and push, with periodic consolidation. Git is the reference sharing/history mechanism; the published format does not specify embedding retrieval, a ranking algorithm, or a measured accuracy guarantee. [SPEC.md](https://github.com/AgentMemoryRepo/agentmemoryrepo/blob/8798cb26c817d451a5ed6cba0ad8d9eca8d5ec3e/SPEC.md), [official page](https://cognition.com/agent-memory-repo).

The installable skill is narrower than the general architecture. Its declared triggers are invocation, requests to remember something, or requests about remembered information. It explicitly adds no hooks, scheduled jobs, or startup scripts. It reads the root and searches/follows links when invoked; saves reusable information; commits after edits; defaults to a separate local repo; and pushes only to a user-requested private remote. It treats memory as contextual data, forbids following commands merely because memory contains them, excludes secrets, and refuses updates in a dirty memory worktree. This skill does not supply autonomous dreaming. [agent-memory-repo/SKILL.md](https://github.com/AgentMemoryRepo/agentmemoryrepo/blob/8798cb26c817d451a5ed6cba0ad8d9eca8d5ec3e/skills/agent-memory-repo/SKILL.md).

## Transferable lessons and limits

### Why Artifacts/isomorphic-git, and whether ytimesy should retain PostgreSQL

**Documented mechanics and rationale:** memoryrepo promises a cloneable memory repository, commit history, and diffs. Artifacts is the remote Git-compatible storage; `isomorphic-git` is the JavaScript Git client that builds and pushes commits inside the Durable Object. They are complementary, not two competing databases. Cloudflare explicitly documents this approach because Workers do not provide a Git binary or ordinary local filesystem. Memoryrepo supplies `memfs` and uses the web HTTP adapter. Its author also documents in a code comment that fresh clones dominated small-write latency, explaining the working-copy cache. No inspected author statement establishes that Artifacts was selected because it outperformed PostgreSQL. [README](https://github.com/supermemoryai/memoryrepo/blob/54f7ff3065df8af687dc5c04a4bb17d6611e5fd1/README.md), [vault.ts](https://github.com/supermemoryai/memoryrepo/blob/54f7ff3065df8af687dc5c04a4bb17d6611e5fd1/src/server/vault.ts), [Cloudflare isomorphic-git example](https://developers.cloudflare.com/artifacts/examples/isomorphic-git/).

One documentation discrepancy matters: Cloudflare's isomorphic-git example says the binding cannot read files, but the current [binding reference](https://developers.cloudflare.com/artifacts/api/workers-binding/) exposes `readFile`, `readBlob`, `readTree`, and `readCommit`, which memoryrepo actually uses. The inspected binding method list has no equivalent commit/write-file method. The sound explanation is binding reads plus Git-protocol writes, not “Artifacts cannot read files.”

**Current ytimesy implementation:** owner checks join memory reads/history to `project.user_id`. Mutations lock the owned project row, optionally reject stale document revisions, and store the updated document plus topic revision history in one database transaction. Consolidation requires a revision. Child/competing sessions cannot mutate shared knowledge. These are concrete benefits already present in the hosted project-memory service; they are not claims about database speed. [Local service source](../../src/server/services/project-knowledge.ts).

**Engineering judgment:** retaining PostgreSQL is a migration-cost and integration recommendation, not an assertion that Git is inferior memory storage. Git offers native cloning, ordinary file tools, branches, inspectable commits, and external editing; those are meaningful benefits if portable, user-owned memory is a product requirement. PostgreSQL fits existing owner-scoped hosted reads, transactional revision writes, and relationships to projects/sessions. Moving the canonical store to Git would require deciding repo provisioning/permissions, external-push freshness, conflict policy, source access, and how database reports and Git memories stay consistent. Keeping both authoritative introduces synchronization work. Exporting Markdown can deliver some portability without canonical Git, but would not provide live bidirectional Git synchronization. Neither storage engine by itself implements better recall, extraction, or consolidation; those depend on the memory lifecycle.

For ytimesy, the useful reference is the lifecycle: compact context at turn start, task-sensitive retrieval, provenance, deliberate durable writes, correction of stale facts, separate consolidation, concurrency checks, and user-visible history. This research does not establish that migrating existing storage to Git or moving the harness to Durable Objects would improve quality. Storage choice and runtime integration require a separate review of the current implementation.

No installed dependencies, provider availability, deployed behavior, recall quality, cost savings, or speedup were tested. No benchmark claim follows from this source review. In particular, prompt instructions alone cannot guarantee correct extraction, successful recall, or faithful source resolution.
