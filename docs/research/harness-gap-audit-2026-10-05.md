# Harness gap audit

Date: 2026-10-05

Scope: compare publicly documented harness mechanics that could improve coding speed and code quality. Research used official README files, documentation and repository metadata. This was read-only upstream research: no installations, runtime tests, benchmarks or paid inference. Documented behavior is not evidence of measured improvement in ytimesy.

Local comparison: the working tree at `278daaa9252c55d5199999b4b795c6a5fa63db91`, including its uncommitted harness changes. This note complements, rather than replaces, the [earlier landscape](coding-agent-harness-landscape-2026-10-03.md). Coverage below is a selected major-harness comparison, not an exhaustive inventory of every agent. Proprietary runtime internals were not audited.

## Conclusion

Ytimesy is not missing the basic multi-agent architecture. Its larger gaps are **model/tool alignment, context discovery, recoverable observations, and efficient coordination/verification**. More builders alone will not fix these. The current read-only-lead design deliberately adds an orchestration step to every coding request; that is a product decision, not a runtime defect.

The last recorded paired run passed correctness in both arms, but ours took 423,874 ms versus native Codex's 192,635 ms (2.20× slower). Both used GPT-6.1 Sol, Medium, Fast off. Ours already ran two isolated builders in parallel and used deterministic integration with no integration-model turn. It still consumed substantially more cumulative input. This is one development task, with asymmetric native request/token limits and unreconciled billing—not a general ranking or causal proof about each feature. [Exact verification and limitations](../../benchmarks/evaluation/VERIFICATION-2026-10-05.md).

## Codex, Claude Code and Cursor

**Codex.** Native Codex can delegate implementation as well as investigation; describing it as sequential-only or its children as incapable of coding is incorrect. Parallel work has token/coordination costs, and concurrent writes need care. Skills load metadata first and instructions when needed. OpenAI also exposes an explicit patch tool. Our ordinary subscription path instead runs the model inside our own loop; it does not automatically inherit native Codex tools, prompts, extensions or behavior. The managed Agents API is another integration surface and must not be confused with that subscription path. [Subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents), [skills](https://learn.chatgpt.com/docs/build-skills), [patch tool](https://developers.openai.com/api/docs/guides/tools-apply-patch), [Agents API](https://developers.openai.com/api/docs/guides/agents-api/overview); local [subscription entry](../../src/server/services/codex-subscription-agent.ts).

**Claude Code.** Skills and compatible MCP definitions load progressively. Older tool outputs can be cleared before conversation summarization. Background shell work has tracked IDs/output files; queued corrections enter after current tool calls. Installed language-server plugins can produce edit diagnostics, but Anthropic cloud sessions do not start those servers. These are environment-dependent capabilities, not a universal stock verification gate. [Architecture](https://code.claude.com/docs/en/how-claude-code-works), [skills](https://code.claude.com/docs/en/skills), [MCP discovery](https://code.claude.com/docs/en/mcp#scale-with-mcp-tool-search), [interactive execution](https://code.claude.com/docs/en/interactive-mode), [code intelligence](https://code.claude.com/docs/en/plugins/code-intelligence).

**Cursor.** Its April harness article explicitly describes model-specific prompts/edit formats and transition instructions when switching models. It also describes per-tool/per-model error monitoring and online/offline quality measurement. Those are useful engineering practices, not proof that every shipped agent always verifies correctly. [Harness engineering](https://cursor.com/blog/continually-improving-agent-harness).

Its September efficiency article reports smaller prompts, on-demand built-in tool definitions, more stable cache layers and less aggressive exploration delegation. Reported savings are Cursor's own experiments, not predictions for us. The lesson is selective context and delegation, not maximizing agent count. [Token efficiency](https://cursor.com/blog/improved-token-efficiency).

Cursor preserves long tool responses as files and provides historical conversation references after summarization. Current Search docs describe local indexed regex search, while older semantic-search URLs redirect and historical articles still discuss semantic search. Do not assert a current detailed embedding architecture from those older articles. Explore/Bash/Browser subagents keep noisy intermediates out of the parent. [Dynamic discovery](https://cursor.com/blog/dynamic-context-discovery), [current Search](https://cursor.com/docs/agent/tools/search), [subagents](https://cursor.com/docs/subagents).

## Open-source harness evidence

Snapshots: [Pi `28dcce2`](https://github.com/earendil-works/pi/tree/28dcce2ba45ce4a9efeb0f5b686f0be830fd89b9), [Oh My Pi `d9ee5e6`](https://github.com/can1357/oh-my-pi/tree/d9ee5e6a31d621f50ac6610cd1cdadccfbf41b0c), [OpenCode `219c226`](https://github.com/anomalyco/opencode/tree/219c2268c327e4312bb4b0843a120d27a340831c), [OmO `becbd1d`](https://github.com/code-yeongyu/oh-my-openagent/tree/becbd1dc6c4569fb1cf33113ca384a81be1a82b5). These are branch snapshots, not release pins; OpenCode documentation was also inspected live.

**Pi.** `badlogic/pi-mono` now redirects to `earendil-works/pi`. Model context uses the active branch of a persisted JSONL session tree; skill descriptions are present while full instructions load on demand. Steering enters after the current assistant turn, while follow-up waits for pending work to finish. Automatic compaction retains recent messages and summarizes goals, constraints, decisions, progress and file operations; original entries remain recoverable. Extensions can transform context, gate tools and customize compaction. Subagents and plan mode are additions rather than core defaults. Current extensions documentation describes built-in MCP support, making older “no MCP” accounts stale. [Architecture](https://github.com/earendil-works/pi/blob/28dcce2ba45ce4a9efeb0f5b686f0be830fd89b9/packages/coding-agent/docs/how-pi-works.md), [compaction](https://github.com/earendil-works/pi/blob/28dcce2ba45ce4a9efeb0f5b686f0be830fd89b9/packages/coding-agent/docs/compaction.md), [extensions](https://github.com/earendil-works/pi/blob/28dcce2ba45ce4a9efeb0f5b686f0be830fd89b9/packages/coding-agent/docs/extensions.md).

**Oh My Pi.** The relevant project is `can1357/oh-my-pi`, a Stencil Labs Pi fork. Default hashline editing uses snapshot tags and rejects unseen ranges; stale snapshots recover only when a unique safe transformation is provable. Model-specific replacement fallbacks exist. Writes use LSP integration when eligible server binaries and cwd markers are present. Batched tasks support async result delivery, schemas and optional workspace isolation; isolation is setting-gated, and default permissive schema validation can accept invalid output with warnings. Speculative compaction computes from a branch snapshot before the threshold. Notes-backed rollover is experimental and off by default; bitmap archives are documented, but their coding-quality benefit was not independently verified. [Edit](https://github.com/can1357/oh-my-pi/blob/d9ee5e6a31d621f50ac6610cd1cdadccfbf41b0c/docs/tools/edit.md), [tasks](https://github.com/can1357/oh-my-pi/blob/d9ee5e6a31d621f50ac6610cd1cdadccfbf41b0c/docs/tools/task.md), [compaction](https://github.com/can1357/oh-my-pi/blob/d9ee5e6a31d621f50ac6610cd1cdadccfbf41b0c/docs/compaction.md).

**OpenCode.** Built-in General supports parallel work; Explore and Scout separate read-only codebase and upstream research. Agents have configurable models, prompts and permissions. Current official documentation says LSP defaults off, automatic compaction on and old-tool-output pruning off. It explicitly acknowledges LSP memory, synchronization and latency tradeoffs and suggests CLI diagnostics where suitable. Plugins can customize compaction context or replace its prompt. [Agents](https://opencode.ai/docs/agents/), [LSP](https://opencode.ai/docs/lsp/), [config](https://opencode.ai/docs/config/#compaction), [plugins](https://opencode.ai/docs/plugins/#compaction-hooks).

**OmO.** Formerly Oh My OpenCode, `code-yeongyu/oh-my-openagent` now promotes standalone OmO Native (`omo-ai`) on its pinned senpi/Pi engine, alongside the OpenCode plugin edition. The latter documents background delegation, completion notifications, output truncation, edit recovery and contextual rules; Team Mode is experimental and off by default. Native README claims programmatic tool batching, durable verification records and companion-model memory. These are maintainer descriptions, not benchmark results, and OpenCode-specific reference sections must not be attributed automatically to Native. [Migration](https://github.com/code-yeongyu/oh-my-openagent/blob/becbd1dc6c4569fb1cf33113ca384a81be1a82b5/docs/guide/migrating-from-opencode.md), [features](https://github.com/code-yeongyu/oh-my-openagent/blob/becbd1dc6c4569fb1cf33113ca384a81be1a82b5/docs/reference/features.md), [README](https://github.com/code-yeongyu/oh-my-openagent/blob/becbd1dc6c4569fb1cf33113ca384a81be1a82b5/README.md).

**Aider.** Sends a token-budgeted repository map of important definitions/signatures, ranked using file dependencies. This is structural context, not simply putting the repository into the prompt. It automatically lints edited files; automatic project tests require configuration. These suggest targeted discovery and feedback, not running the entire suite after each edit. [Repository map](https://aider.chat/docs/repomap.html), [lint/test behavior](https://aider.chat/docs/usage/lint-test.html).

**Cline and Goose.** Cline documents resumable tasks, Git-based file checkpoints and automatic compression, while warning that long tasks can lose earlier details. Goose documents parallel subagents, configurable MCP extensions and reusable workflow recipes. These are established continuity/extensibility patterns, not evidence that either outperforms our paired control. [Cline tasks](https://docs.cline.bot/core-workflows/task-management), [Goose](https://block.github.io/goose/).

## Cloud harness evidence

**Capy.** Its documented server loop overlaps first inference with execution-machine boot. Children have independent prompts/conversations, shared-reader versus fresh-writer placement, stacking, parent completion notifications and on-demand interim inspection. Skills use metadata first/full-body later. PR events can wake the owning thread for checks/reviews. These public documents do not reveal its private decomposition algorithm or prove which native subscription harness it uses. [Machines](https://docs.capy.ai/machines), [subagents](https://docs.capy.ai/subagents), [skills](https://docs.capy.ai/skills), [PR events](https://docs.capy.ai/pull-requests).

**Hoplite.** Its October 3–4 changelog describes prepared-context and checked-message reuse with invalidation, context checks overlapping response preparation, reads during dependency setup, verified-auth reuse across handoffs, idle backups and asynchronous diff refresh. No comparative latency proof accompanies those claims. Project/root/nested instructions and skills are explicit context surfaces. PR repair is bounded rather than indefinite. [Changelog](https://hoplite.sh/changelog), [agent context](https://hoplite.sh/docs/agent), [skills](https://hoplite.sh/docs/agent/skills), [PR repair limits](https://hoplite.sh/docs/github).

**Devin.** Dynamic Workflows support per-item pipelines rather than whole-stage barriers, structured outcomes and reuse of completed calls on resume; unfinished work restarts and changed call inputs invalidate matches. Default child execution uses separate VMs and branch handoffs. Docs recommend simpler sessions for small/tightly coupled work. Browser testing is a selected principal-flow sanity check, not exhaustive CI. [Workflows](https://docs.devin.ai/work-with-devin/dynamic-workflows), [managed children](https://docs.devin.ai/work-with-devin/advanced-capabilities), [testing](https://docs.devin.ai/work-with-devin/testing-and-recordings).

**Vorflux.** Its approved dependency plan dispatches independent builds in parallel and sequences prerequisites. Skills, source-visible memory and browser evidence are documented; a periodic repository-skill rescan is not proof of branch-fresh discovery. Inspected docs do not establish arbitrary child-peer messaging or exact workspace-isolation semantics. [Plan](https://vorflux.ai/docs/plan-mode), [skills](https://vorflux.ai/docs/skills), [memory](https://vorflux.ai/docs/memory), [testing](https://vorflux.ai/docs/testing).

## Concrete gaps and their likely consequences

“Missing” here means not present in the inspected active cloud-tool/model path, not an exhaustive proof about every historical adapter.

1. **Model-aligned editing — missing.** Cloud writers get `create_file` and exact `replace_text`; there is no model-specific patch tool in that catalog. OpenAI and Anthropic therefore use the same edit protocol despite different native conventions. Matching edit tools to model families is a high-priority candidate for fewer retries and reasoning tokens. Do not replace guarded edits with arbitrary writes or discard exact-review identity. [Our file tools](../../src/server/services/api-agent-file-tools.ts); comparison: Cursor's harness article and OpenAI's patch guide above.

2. **Progressive tool/skill discovery — missing in the active cloud path.** `model-agent-loop.ts` serializes every tool schema and sends the entire `ToolSet`; there is no discovery/active-tool selection. `api-turn.ts` injects shared orchestration and project knowledge, but does not discover a repository skill catalog or automatically resolve nested instruction scope. “Read repository instructions” leaves that work to the model. Keep frequent tools available; demand-load infrequent capabilities and task-relevant skills. Do not turn startup discovery into another VM-blocking first-token delay. [Loop](../../src/server/services/model-agent-loop.ts), [turn assembly](../../src/server/jobs/api-turn.ts).

3. **Recoverable output and stronger search — partial.** Single-file reads now have continuation, and archived conversation search already exists. But `search_files` uses tracked-file `git grep`, at most five matches per file, then a 32,000-character slice with no result cursor. Synchronous shell/diff/list outputs also use fixed slices. Command files retain output locally, but `read_command` returns only the tail without a paging interface. Archiving a truncated tool result cannot recover text never returned. Add bounded output artifacts/cursors and intentional untracked-file search before assuming we need embeddings. A symbol/dependency map is a separate possible improvement, not an implemented semantic code index. [Tools](../../src/server/services/api-agent-tools.ts), [file tools](../../src/server/services/api-agent-file-tools.ts), [commands](../../src/server/services/api-agent-command-tools.ts).

4. **Revision-scoped discovery reuse between builders — partial.** Prepared environment snapshots and project Markdown already avoid some setup/knowledge repetition. They are not a branch-validated packet of applicable instructions, relevant source observations, interfaces and verification commands. Each standalone child can rediscover the same material. A small reusable evidence packet should bind observations to repository/base revision and content hashes, invalidate on changes, and exclude secrets/unrelated parent conversation. Do not convert previous agent claims into trusted facts. [Knowledge selection](../../src/domain/project-knowledge.ts), [turn preparation](../../src/server/jobs/api-turn.ts). Hoplite's documented invalidation is a useful precedent, not proof our implementation will be faster.

5. **Cheap edit-time feedback — missing as an automatic cloud-tool step.** The edit path returns path/hash, not syntax/type diagnostics. Builders can already run CLI checks; `verify_changes` only checks diff whitespace/status. Selective syntax/lint/type feedback could catch mistakes earlier. Persistent LSP is one option, not an unconditional requirement: account for server startup, memory, stale diagnostics and language support. Do not launch full-project compilation after every keystroke or confuse diagnostics with behavioral correctness. [File tools](../../src/server/services/api-agent-file-tools.ts); Aider, Oh My Pi and OpenCode references above.

6. **Scheduling/verification efficiency — partial.** Our policy already launches independent builders together and reviews as they finish. It still relies on model-chosen splits; it has no inspected critical-path estimator. Deterministic integration imports and runs checks sequentially. Parallelize only checks proven independent at an immutable combined revision and safe for shared files/resources. Do not parallelize arbitrary package scripts, accept a partial result, weaken full final checks or replay uncertain commands. [Policy](../../src/domain/agent-orchestration.ts), [check execution](../../src/server/services/automated-task-integration.ts).

7. **Per-tool/model quality feedback — partial.** We persist activity, usage and safe turn failures and have product analytics. The inspected analytics schema reports coarse turn/runtime outcomes, not per-tool/model error categories, p95 tool latency, duplicate-read frequency or repair counts. Those measurements would distinguish infrastructure wait, model deliberation, redundant context and edit failures without collecting private source or reasoning in PostHog. [Analytics schema](../../src/domain/analytics.ts), [turn analytics](../../src/server/services/turn-analytics.ts), [failure policy](../../src/domain/api-turn-failure.ts).

## Product decisions, not automatic fixes

- The mandatory read-only lead means even a tiny code change must create a builder. Native direct-writing agents avoid that extra handoff. Keeping this boundary is compatible with our design, but we must reduce its tax rather than pretend it is free. Changing it requires a deliberate product decision.
- More parallel agents help only when independent useful work exceeds launch, cold-context, coordination and integration costs. There is no basis to hardcode three builders for every request.
- Provider-compatible compaction and history retrieval already exist. Speculative compaction, bitmap archives, an embedding service and a large plugin framework are not proven priorities for our measured bottleneck. Preserve opaque state and cache prefixes if adopting any pruning/discovery mechanism.
- Automatic post-PR repair matters for reducing human interruptions, but it is distinct from the measured time to the first integrated correct result. Do not add unrelated PR automation to this speed-improvement batch.

## Recommended order before another live comparison

1. Model-aligned patch editing, with existing write/read-only scopes and review receipts preserved.
2. Role-scoped core tools plus deferred discovery, compact role guidance and discoverable skills/instructions.
3. Complete recoverable observations and stronger lexical search; revision-validated shared discovery packets.
4. Selective diagnostic feedback and safe independent-check overlap; better phase/error instrumentation.

Reuse maintained provider/platform mechanisms where compatible rather than building a new generic agent framework. First prove tool contracts, cache-prefix stability, permissions, complete-output retrieval and invalidation with small local tests. Then run one frozen paired batch across independent and tightly coupled tasks, with unchanged protected checks, equal model/reasoning/Fast settings, comparable limits and reconciled cost. Speed, cost and correctness remain competing measured objectives; this research cannot guarantee superiority.
