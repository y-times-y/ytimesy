The system in one minute

The browser is a viewer and control surface. The database holds projects, sessions, task rows, transcripts, and task completion events. Freestyle holds each machine and its running provider process. These pieces are linked by services in the web process and a separate job worker.

1 · BrowserComposer, task panel, Files, Diff, Terminal, Desktop
2 · Server entryAuthenticated TanStack functions and API routes
3 · ServicesChoose session, VM, provider, task action, publication
4 · StatePostgreSQL rows, pg-boss jobs, event outbox
5 · ExecutionFreestyle VM, Codex app server or Claude CLI

Project

GitHub repository and branch plus one prepared workspace record and snapshot.

prepare-workspace.ts · workspaces.ts

Session

A conversation row. A root chat, child task, and legacy side chat all use the same table.

agent-sessions.ts · agent-task.ts

Machine

A Freestyle VM identified by provider_ref. A writer gets its own VM; a read-only child can share its parent's VM.

agent-session-machine.ts · session-workspace-machines.ts

Effect coordinates many server workflows, while database adapters commonly return Promises. Freestyle and provider calls are wrapped as effects at service boundaries. Effect does not persist a running effect across a server restart.

End-to-end workflow today

Follow a single user's task from account connection to publication. Each step names the code that currently owns it.

Sign in and authorize a repository

Better Auth identifies the user. The GitHub App flow grants selected repository access. The server validates ownership before storing a project and its branch.

auth.ts · projects.ts · github.ts

Queue project preparation

A project gets a workspace row. pg-boss runs preparation: boot or recover a VM, clone the repository, install dependencies, seal a private snapshot, and pause the template VM. An hourly job can rebuild a changed snapshot.

workspaces.ts · queue.ts · prepare-workspace.ts · refresh-workspace.ts

Connect a runtime

Codex device sign-in or Claude's own sign-in runs inside a VM. A successful login can be captured as a private Freestyle snapshot and its ID stored encrypted in agent_account. API keys are an alternate explicit connection path.

persist-codex-auth-snapshot.ts · persist-claude-auth-snapshot.ts · agent-account.ts

Open a root chat

The UI first creates a session row. Connect or Send binds a VM by resuming its saved provider_ref or copying a snapshot. The provider adapter reports listed models and auth status.

agent-session.fn.ts · agent-session-machine.ts · harness-workspace-session.ts

Send a turn

The user's message is saved before the provider accepts the turn. Codex uses a Python daemon talking to its app server; Claude uses its CLI and a local MCP task-tool server. Transcripts and status are read back into the session row.

persist-session-view.ts · login-daemon.py · claude/login-session.ts

Inspect the work

Files reads the selected session's checkout, Diff shows changes, Terminal opens a PTY, and Desktop exposes a shared Linux display. These tools are tied to the session VM; a paused machine may need to wake before interactive use.

workspace-explorer.ts · workspace-terminal.ts · workspace-desktop.ts

Publish deliberately

A separate action configures commit identity, commits the workspace, pushes a branch with a temporary installation token, and opens a draft PR. Delegated tasks add a review-state check before their publication tool proceeds.

publication.ts · harness-workspace-session.ts

How delegated tasks work

The lead decides whether to delegate from prompt instructions. The control plane validates placement, depth, access, and stacked dependencies. A task is a child agent_session row, so a child can become a parent.

DraftTitle, standalone prompt, model, access, placement, dependency
StartCheck depth ≤ 3 and predecessor; choose shared or fresh VM
RunChild gets its own provider turn; read-only mode is requested where appropriate
Wake parentCompleted, failed, or blocked summary enters durable event table
Review / PRLead inspects diff, marks reviewed, then may publish

Shared read-only child

Reuses the parent's exact checkout. A wrapper changes known /tmp daemon paths so concurrent conversations do not overwrite each other. Provider read-only permissions are also requested.

session-workspace-machines.ts · agent-session-machine.ts

Fresh writing child

Copies a snapshot into its own VM. Parallel tasks start independently; a stacked task waits for its sibling predecessor to be completed, reviewed, and published, then checks out that PR branch.

agent-task.ts · agent-session-machine.ts

Task tools exchange one JSON request and response through VM-local files. A web-process loop services these requests every second for at most 1,800 polls, about 30 minutes. The completion event becomes durable after the result is observed and saved; the running command and its supervision are not durable across process loss. Source: harness-workspace-session.ts

A concrete example

Suppose the lead is asked to fix a failing API and audit the UI. It can create two drafts: a fresh read-write API task and a shared read-only UI audit. Starting the API task copies a project snapshot into a new VM. Starting the audit keeps the lead's VM and checkout, with separate daemon files. Either child may delegate again until depth three. When the API child finishes, its summary is saved, an event is queued, and an idle parent receives a follow-up. The lead can inspect its diff and mark the result reviewed before opening a PR. If the server disappears before the result is observed, that last handoff is not guaranteed by the current supervisor.

There are two task-start routes: the human task panel calls a server function, and a model calls start_task. Both perform binding and sending in separate implementations.

The snapshot story, precisely

There is a user login snapshot, a project environment snapshot, and a per-session machine copy. Their relationship depends on which existed when project preparation ran.

What current code does
  • Project preparation prefers the user's Codex auth snapshot if already connected; otherwise it uses the tools image. It then clones and installs the repository and seals a project snapshot.
  • For a new Codex session, the binding path does not pass the saved Codex auth snapshot. It copies the project snapshot. This works for auth only when that project snapshot was prepared from a still-valid Codex login.
  • For Claude, session binding passes the Claude auth snapshot, which takes priority over the project snapshot. The repository may then have to be cloned into that session VM on Send.
  • A project prepared before Codex login is not automatically rebuilt from the newly saved login snapshot.
Coherent intended contract
  • Capture each user's provider login once in a private snapshot.
  • Prepare a versioned project template for that user and provider: authenticated base, repository, dependencies, and setup.
  • Copy that combined template for every writer; clear only conversation and runtime scratch files.
  • Refresh or invalidate templates when login, project source, or environment recipe changes.

Evidence: prepare-workspace.ts · workspace-boot-snapshot.ts · agent-session.ts · agent-session-machine.ts · codex-workspace-session.ts

Important correction: “Codex child VMs never have credentials” would be too broad. They may inherit credentials from a project snapshot prepared after Codex login. The actual defect is that authentication depends on that preparation history and is not guaranteed for every new Codex VM.

Repeated logic and unnecessary coupling

These are consolidation candidates. The finding names the duplication and its consequence; it does not imply every similar line should become a generic helper.

P0Two task-start implementations

The UI server function and model tool both validate a draft, bind a child VM, send the task, and mark failure. Changes to start semantics can land in only one path. One service should own task start; both callers should use it.

agent-session.fn.ts:218 · harness-workspace-session.ts:622

P0Two wrap-up implementations

Human and model paths each stop and send a wrap-up prompt, with different wording and Claude interruption checks. They can disagree on behavior. One task command should own this transition.

agent-session.fn.ts:282 · harness-workspace-session.ts:733

P1Clone/install repeated across lifecycle stages

Initial preparation and hourly refresh repeat branch resolution, token file creation, cloning, bot hook setup, install, snapshot, and event recording. A narrower shared preparation operation could keep setup behavior consistent while each job retains its distinct failure policy.

prepare-workspace.ts · refresh-workspace.ts

P1Task tool contract duplicated in Python

Codex dynamic tools and Claude MCP tools separately declare names, arguments, and descriptions. The TypeScript parser is a third copy of the accepted names. Schema drift can make one provider expose a tool that the control plane interprets differently.

codex/login-daemon.py:93 · claude/task-tool-server.py:1 · agent-task-tool.ts:35

P1Task state written through several routes

Direct task-state updates, transcript persistence, and turn-status updates each map provider status into task_state. The same row also represents root sessions and legacy side chats. This makes transition rules hard to audit and permits state changes outside one owner.

agent-sessions.ts:252 · agent-sessions.ts:326 · agent-sessions.ts:360

P2Legacy side chat shares task hierarchy

Side chat is identified by the title string “Side chat” and filtered out of task lists. That is a fragile implicit type. Its creation and provider-specific read paths also live inside the large harness session service.

agent-sessions.ts:141 · harness-workspace-session.ts:1240

P2Large provider dispatch module

The harness session service currently owns provider connection, turns, polling, task-tool dispatch, side chat, view mapping, and stop behavior in one module. Separating lifecycle ownership from provider adapters would make the actual control path easier to test.

harness-workspace-session.ts

P2Benchmark policy is a second prompt

The benchmark file carries its own delegation text and a 3-direct/8-total cap. The product prompt has different rules. Comparing them as though they were the same harness would be misleading.

Where the current flow can fail

Auth depends on snapshot timing

A new Codex VM may work if the project snapshot inherited login; a project built earlier may not. Claude takes the auth snapshot over the ready project snapshot and may redo checkout preparation.

agent-session-machine.ts:301

Supervision is local to one process

The 30-minute loop and in-memory in-flight set are not leases. Restarting the server or hitting the cap can leave a running provider without reliable result observation.

harness-workspace-session.ts:446

Fresh grandchild after shared child

The fresh grandchild can inherit a wrapper that scopes paths to its shared parent, while later callers address unscoped paths. This can break follow-up and control messages.

session-workspace-machines.ts:78

Capacity has no admission queue

Freestyle capacity errors receive short retries, then fail. There is no durable “start when a writer slot opens” state or budget per task tree.

agent-session-machine.ts:584

Review is a state flag

The lead can inspect a diff and set “reviewed.” The code does not create a reviewer task automatically, store structured findings, or cycle through repair and re-review.

harness-workspace-session.ts:662

No comparable performance run

The current Python adapter does not invoke the product's VM task path. Run manifests, raw trajectories, model cost, VM cost, repetitions, and scoring receipts are absent.

local_orchestration.py:23

Browser closed versus server restarted

Browser closes
  • The VM and its provider process may continue.
  • The web-process supervisor can continue while that process stays up.
  • The saved transcript lets a later browser reconnect.
Web process restarts
  • Its polling loop and in-memory in-flight set disappear.
  • pg-boss can still deliver events that were already persisted.
  • There is no complete worker that reattaches to every active turn and recovers its missing completion event.

What this audit did not prove

It did not access a live Freestyle account, execute a complete private-repository task, deploy migrations, or run the benchmark. Those require separate live verification. It also did not change the application logic.

A coherent target workflow

The order matters because the benchmark and review loop depend on a working, recoverable task runner.

One provider-aware project template

Build a combined private template from the user's authenticated provider snapshot plus the prepared repository. Store its source auth version and project version. Copy it for each writer.

One durable task command service

Have UI actions and provider task tools call the same create, edit, start, message, wrap-up, review, and publish operations. Persist command IDs and outcomes so retries do not duplicate VMs or PRs.

Recoverable supervision

A worker claims active turns with leases, periodically reconciles provider status, records completion, and restarts observation after process loss. Event delivery wakes an idle parent exactly once in effect.

Explicit verification and review

Attach success criteria and named checks to each task. A reviewer records findings against a specific diff revision; repair and re-review have bounded iterations and a clear exit condition.

Benchmark the same path users run

Feed tasks through the product control plane and fresh writer VMs. Pin task set, model, reasoning, hardware, limits, and repetitions. Record raw traces, pass rate, time, token cost, and VM cost.

Definitions used in this report
Template
A saved Freestyle snapshot used as the starting disk for another VM.
Writer
A task allowed to modify files; its intended placement is a fresh VM.
Shared child
A read-only task on the parent's VM and checkout, with separately scoped daemon files.
Outbox
A database record of a completed, failed, or blocked child result waiting to be delivered to its parent.
Control plane
The app and worker code that owns task rows, VM binding, commands, results, and publication.
