# Y and Y²

Status 2026-11-12: built behind a per-project switch (Project settings → Y → "Use Y and Y²", `project.y_enabled`) and the harness variant `y=on` for eval users. Off by default. Not yet run end to end on real VMs.

## Layers

| Layer | One per | Does | Tools |
|---|---|---|---|
| **Y²** | project | Watches every thread and tells the person what is going on: what needs them, what is working, what finished with its pull request. Never works. | `threads`, `thread`, `start_thread`, `message_thread`, `stop_thread`, `ask_user` (`src/domain/y-squared.ts`, `src/server/services/y-squared-tools.ts`) |
| **Y** | thread (chat) | The agent the person talks to. Hands every change to builders, asks readers for code facts, reports in ≤100 words. Never changes, runs or reads code. | `agent`, `agent_send`, `ask_user`, `request_project_secret` (`src/domain/y-agent.ts`) |
| **Builders** | piece of work | Today's builder harness as writer subagents on forks of the thread's VM. Not conversational: brief in, report out. | the full harness |
| **Subagents** | — | Bounded helpers under a builder, as before. | as before |

Why Y does not execute: DeepSeek's Super-agent essay (Nov 1 2026, section 2.1): the router "is designed not to execute tasks itself" so the single node every message reaches is not a bottleneck, and in their ablation a single session told to delegate often did the work itself anyway.

## How work reaches the pull request

1. Y starts a builder (`agent`, role writer) with a self-contained brief.
2. The builder works on its fork; at the end the runtime exports its patch to Y's VM, as for any writer.
3. With Y on, the runtime applies the patch to Y's checkout (`applyWriterPatchToParent`): `git apply --index --check`, then apply. A patch that does not apply cleanly changes nothing; Y is told why and starts a builder to resolve it. No conflict markers are ever committed.
4. Y's turn always commits (an empty commit is skipped) and publishes to the thread's branch and pull request, as a chat does.

## Y² write tools

`start_thread(title, brief)`, `message_thread(id, text)`, `stop_thread(id)` (`src/server/services/y-squared-tools.ts`, schemas in `src/domain/y-squared.ts`). Y² runs threads like a captain; it still never works and has no VM.

- **Start.** A new root chat in the project through the person's own send path (`sendComposerMessage`, `createNew: true`, Y²'s own model); the first line of the message is the title. The result says `Started` (the turn is running) or `Queued … behind the budget/concurrency limit`.
- **Message.** The id must be a root thread of the same project, not Y² and not a subagent (metadata row only: `agentSessionMetadataForOwner`, never the transcript). A running thread queues the message behind its turn (or takes it at its next step with `mode: "steer"`); an idle one starts a turn. Same `sendComposerMessage`, so the existing queue applies. Not `queueAgentPeerMessage` (parent→child only, reads transcripts). Messages and briefs are capped at 8,000 characters.
- **Stop.** `stopTurnKeepingQueue`, the Stop button's path, for a running thread.
- **Admission.** Every VM start goes through the usual turn start: per-user turn concurrency (32), usage windows, Freestyle usage and Cloudflare budget admission. There is no new thread cap. `Y_SQUARED_MAX_STARTS_PER_TURN` (8) only bounds a runaway loop in one Y² turn (per tool instance; one instance per step).
- **Idempotency.** Each send is keyed by Y²'s turn id and a hash of its content, so a replayed step does not start or send twice.
- **Cost.** No polling, no new Durable Object request: the tools read one Postgres metadata row per message/stop and none for start. Y² is woken by the crew as before when a started thread finishes or needs the person.
- **Turn rules.** The three tools count as workspace-neutral in `turn-saving.ts` (like `threads`): Y² has no checkout, and a turn that counted them as changing one would fail on "Y² has no workspace". Y² never commits.
- **Gating.** The tools exist only in Y²'s own turn (`ySquared` in `api-turn.ts`).

## Crew status and wakes

Y² does not read thread transcripts. Each Y project has one `YSquaredCrew` Durable Object (`src/server/edge/y-squared-crew.ts`, named by project id, SQLite, binding `Y_SQUARED_CREWS`, migration v5).

- **Rows.** `crew(session_id pk, title, state, waiting_on, pr_url, last_reply ≤300 chars, updated_at, created_at, last_request ≤200 chars, last_active_at, working_since, start_wake_at)`: one row per thread, rewritten in place (`created_at` = first note, 0 when not recorded; `last_request` = the person's last request, never a wake; `last_active_at` = last turn start/settle note, i.e. when the person or a wake used the thread; `updated_at` keeps its meaning of the last row write). The three columns were added to the deployed table additively: the store checks `pragma_table_info('crew')` at start and `alter table … add column`s the missing ones once; old rows keep working (created "not recorded", last active = their `updated_at`, no request until the thread's next settle note); an identical note writes nothing; rows untouched for 30 days are pruned (at most daily). `working_since` is set by the start note (kept by repeats, cleared on settle). `wake_state` holds `pending`, `pending_due_at`, `last_wake_at`, `last_heartbeat_at`, `wakes_this_hour`, `hour_start`, `alarm_at` (and the wake target); `wake_events` (≤12 rows: what changed since the last wake) and `y2_sent` (Y²'s own sends) are the two small tables added for the wake message. All columns and tables are added additively at start.
- **Push on transitions.** A thread's `ModelConversation.noteTurnStatus` also calls `noteThread` when its turn starts (`working`) and when it settles (`waiting` on the person / `finished` / `failed`), fire and forget under `waitUntil`, errors swallowed. What it waits on, its pull request and last reply come from the transcript copy the chat object already holds (`chatWaitingOn`, `threadHistoryFacts`): no Postgres read. The last request is the last non-wake `userMessage` of that same copy, so it is sent with the settle note (the start note carries none and keeps the stored one): while a thread is still working on a new request, `last request` shows the previous one until it settles. The chat's project, `project.y_enabled` and its Y² id come with the scope `resolveModelConversation` already reads each step (one join, no extra round trip) and are kept in the chat's SQLite (`crew_scope`, written only when they change). A chat of a project without Y, and Y² itself, send nothing (`crewProjectFor`). The switch is refreshed at the next turn start.
- **Wake policy** (`crewWakeDelayMs`, `heartbeatDueAt` in `src/domain/y-squared-crew.ts`; `SqliteYSquaredCrew.noteThread` / `takeWake`). A thread TURN settling (`finished`, `waiting` on the person, `failed`; every turn, not only a whole thread done) sets `pending` and a due time `max(now + d, last_wake_at + d)` with d = 5 s for `waiting` / `failed` and 10 s for `finished` (was 15 / 30); a later urgent note pulls an already-set alarm earlier, never later. Plain progress never wakes. Three more things can fire the one alarm: a long-running **heartbeat** (below), and **a thread the person started directly** (below). The alarm sends exactly one Y² turn through the normal send path (a hidden wake message, shown as a silent wake notice) whose text lists what changed since the last wake and who is still working (`crewWakeBody`), then records `last_wake_at`. At most **24** wakes per hour per project (was 12); the 25th stays pending and fires when the hour window rolls over (a held heartbeat is not left pending: the next window re-checks it). A failed enqueue hands the wake back (and keeps its changes) and re-arms the alarm itself: retries after 30 s, 1 min, 2 min, then 5 min, 8 tries in all (`runCrewAlarm`, `src/server/edge/crew-alarm.ts`); after that the next note re-arms it. Y²'s own session id never wakes it.
- **Heartbeat.** While any thread has been `working` (`crew.working_since`) for more than 5 minutes with no wake since (the clock of a thread is `max(working_since, last_wake_at)`), the same project alarm is set for `max(quiet + 5 min, last_heartbeat_at + 10 min)`: at most one heartbeat wake per project per 10 minutes, so again every 10 minutes while threads keep working. No polling and no extra alarm: `rearm` picks the sooner of the pending wake and the heartbeat, only when something is pending or working (a project with nothing working has no alarm; a stale alarm that fires with nothing to do arms nothing). A row `working` for over 6 hours is taken for a lost settle note and gets no more heartbeats. The wake message says which threads are still working and for how long, so Y² posts one brief "still working" line.
- **Direct starts.** When a thread's start note carries a request (`crewRequestFromStartItems`: the last item of the chat copy is a non-wake user message) and Y² did not send it, the person messaged the thread directly: Y² is told at its next wake ("You were not part of this: <thread> got <request>") and, at most once per thread per 10 minutes (`crew.start_wake_at`), woken for it (10 s debounce). Y² marks its own sends first (`noteY2Sent`, one extra crew request per `start_thread` / `message_thread`, a `y2_sent` row valid for 60 minutes, used once), so a thread Y² started or messaged never wakes it (Y² narrates those itself). A start with no request (a wake, an automatic turn) is neither.
- **Reading.** Y²'s `threads` is one `list()` request, `thread` one single-row request. An empty, never-filled crew is filled once from `listSidebarAgentSessions` metadata (no items), then marked reconciled. Without a binding (local development) the tools read that metadata only. Both tools show `last active <relative>`, `created <date>` (or "not recorded"), the last request and the last reply (≤6 short lines per thread in `threads`; order stays needs-the-person, working, then most recently active). `ySquaredInstructions` tells Y² to answer "which thread did X / was last used / created Y" from those, to say plainly what is not recorded (who or which agent built Y² itself, work outside the project's threads, anything older than the crew's records) with a next step (open the most recently active thread or ask it with `message_thread`), and never to mention failures unrelated to the threads.
- **No user MCP servers.** A Y² turn never loads the user's configured MCP servers (`runApiTurn` skips `connectableMcpServers` for Y²) and so never adds the "MCP servers unavailable this turn" notice; on the Claude runner-box route only ytimesy's bridge server is in `mcp.json` (the runner already sets `strictMcpConfig`). `noteThread` accepts the first deploy's older shapes (`turnStatus`, `pullRequest`, `reply`).

Cost per thread-turn (the new columns ride the same upsert): 2 notes (start, settle) = **2 crew requests** (3 when it ends on a card for the person: the waiting hint), ≤2 row writes plus ≤2 `wake_state` / `wake_events` writes. A wake adds 1 alarm invocation, ≤3 `wake_state` writes, one normal Y² turn (model cost: API tokens, or the person's plan usage on the Claude runner) and its `threads` read (1 request). A Y² `start_thread` / `message_thread` adds 1 mark request. A Y² overview read is 1 request, 0 writes.

## Staying in the loop

The owner's feedback: Y² reported only once a thread was done. What keeps the person in the loop now, and what each part costs.

- **Live status card** (`src/features/workspace/y-squared-card.tsx`, data in `src/domain/y-squared-card.ts`): pinned at the top of the Y² chat; "Waiting on you / In progress / Done recently" with status icon, title, a **client-side elapsed clock** (`elapsedClock` from `workingSince`, ticking once a second only while something works), the person's last request (≤120 chars), what it waits on and a PR link; needs-you first. **No model call, no timer-driven request.** Its rows are the sidebar's chat list (`['agent-sessions', projectId]`), which the user's hub already refreshes when a chat's turn changes; the crew's last request / PR come from one `readYSquaredCrewCard` request (one DO `list()`) per change of the rows' status signature (`cardSignature`), never on a clock. The crew read can lag the row by one note when both change together (it then shows the previous request until the next change).
- **Narration at meaningful moments only** (the wake policy above): turn finished / needs the person / failed (5 s, 10 s debounce), a long-running heartbeat, a thread the person started directly. `ySquaredInstructions` makes each wake a short delta, a one-line acknowledgement when Y² starts or steers threads, terse replies to terse commands, and a pointer to the card instead of repeating it.
- **`message_thread` modes**: `queue` (default: a waiting row, `released: false`, that starts the thread's next turn when the running one ends; several wait in order, at most 50 per chat), `steer` (a running thread: the same row stored already `released: true`, the mark Send puts on a person's queued message, so the thread takes it at its next model step with no extra turn; a Claude Code run takes released rows only after its next tool call, and a turn on a runner box may see it up to 10 s late, docs/turn-runner-boxes.md; if the turn ends first the row starts the next turn; an idle thread starts a turn as for any send), `interrupt` (stops the running turn through `stopTurnKeepingQueue`, then sends). The old text said `steer` was `queue`; that was wrong for root chats.

Estimated DO requests (per project, not counting the threads' own objects or the user hub): a busy hour with 10 thread-turns is 20 notes + ≤10 wakes × 2 (alarm + `threads`) + ≤6 heartbeats × 2 = **≈50 requests/hour**; the ceiling is 24 wakes × 2 + 20 notes + ≤10 marks ≈ **80/hour**; an idle project costs 0 (no alarm, no polling). Opening the Y² chat adds 1 request per status change (≈ one per thread-turn edge). Against ~10k DO requests per user per month (`docs/cloudflare-budget.md`) that is ≈12 hours of continuous heavy work at the ceiling, ≈25 at the busy-hour estimate. Plan usage: each wake is one short Y² turn; at most 24 per hour per project, of which at most 6 are heartbeats, 2 per thread-turn is the typical case. Wake rate is the dial: lower `CREW_WAKES_PER_HOUR` or raise `CREW_HEARTBEAT_EVERY_MS`.
