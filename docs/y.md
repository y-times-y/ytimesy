# Y and Y²

Status 2026-11-12: built behind a per-project switch (Project settings → Y → "Use Y and Y²", `project.y_enabled`) and the harness variant `y=on` for eval users. Off by default. Not yet run end to end on real VMs.

## Layers

| Layer | One per | Does | Tools |
|---|---|---|---|
| **Y²** | project | Watches every thread and tells the person what is going on: what needs them, what is working, what finished with its pull request. Never works. | `threads`, `thread`, `start_thread`, `message_thread`, `stop_thread`, `schedule`, `view_image`, `ask_user` (`src/domain/y-squared.ts`, `src/server/services/y-squared-tools.ts`) |
| **Y** | thread (chat) | The agent the person talks to. Hands every change to builders, asks readers for code facts, reports in ≤100 words. Never changes, runs or reads code. | `agent`, `agent_send`, `ask_user`, `request_project_secret` (`src/domain/y-agent.ts`) |
| **Builders** | piece of work | Today's builder harness as writer subagents on forks of the thread's VM. Not conversational: brief in, report out. | the full harness |
| **Subagents** | — | Bounded helpers under a builder, as before. | as before |

Why Y does not execute: DeepSeek's Super-agent essay (Nov 1 2026, section 2.1): the router "is designed not to execute tasks itself" so the single node every message reaches is not a bottleneck, and in their ablation a single session told to delegate often did the work itself anyway.

## How work reaches the pull request

1. Y starts a builder (`agent`, role writer) with a self-contained brief.
2. The builder works on its fork; at the end the runtime exports its patch to Y's VM, as for any writer.
3. With Y on, the runtime applies the patch to Y's checkout (`applyWriterPatchToParent`): `git apply --index --check`, then apply. A patch that does not apply cleanly changes nothing; Y is told why and starts a builder to resolve it. No conflict markers are ever committed.
4. Y's turn always commits (an empty commit is skipped) and publishes to the thread's branch and pull request, as a chat does.

## Y² write tools

`start_thread(title, brief, attachments?)`, `message_thread(id, text, attachments?)`, `stop_thread(id)` (`src/server/services/y-squared-tools.ts`, schemas in `src/domain/y-squared.ts`). Y² runs threads like a captain; it still never works and has no VM.

**Attached images.** Y² has no machine, so an attachment is never a path to it. The attachment note it reads names each file ("The person attached shot.png (image, 120 KB). Use view_image to look at it.", `ySquaredAttachmentNote`, applied to every model input of a Y² turn, API/Codex/Grok and Claude runner alike) and never mentions /tmp. `view_image(attachment)` resolves a name, id or old-style path against the user messages of THIS chat only, reads that one object (`downloadMessageAttachment`, owner-checked) and returns just the image part (`toModelOutput`); over 3 MB it refuses by size (no image library to scale it down), non-images are refused. Persisted history (`checkpointApiTurn`/`finalizeApiTurn`) swaps a viewed image's bytes for a one-line note, so later steps and turns carry text; wakes, crew rows and `threads` output never carry bytes. `attachments` (max 4 names/ids from this chat) on `start_thread`/`message_thread` hands each file's bytes to the send path as the person's own attachments, so the target chat stores its own copy under its own id (builders then find them in the VM as usual). Limits stay 8 files, 10 MB each, 20 MB total.

- **Start.** A new root chat in the project through the person's own send path (`sendComposerMessage`, `createNew: true`, Y²'s own model); the first line of the message is the title. The result says `Started "<title>" (id <id>)` (the turn is running) or `Queued "<title>" (id <id>) … behind the budget/concurrency limit`: the id lets Y² open, message or link the thread at once (before 2026-11-23 it got no id and could not). `thread` on an id the crew has not noted yet (just started, queued) answers from that chat's own metadata row.
- **Message.** The id must be a root thread of the same project, not Y² and not a subagent (metadata row only: `agentSessionMetadataForOwner`, never the transcript). A running thread queues the message behind its turn (or takes it at its next step with `mode: "steer"`); an idle one starts a turn. Same `sendComposerMessage`, so the existing queue applies. Not `queueAgentPeerMessage` (parent→child only, reads transcripts). Messages and briefs are capped at 8,000 characters.
- **Stop.** `stopTurnKeepingQueue`, the Stop button's path, for a running thread.
- **Admission.** Every VM start goes through the usual turn start: per-user turn concurrency (32), usage windows, Freestyle usage and Cloudflare budget admission. There is no new thread cap. `Y_SQUARED_MAX_STARTS_PER_TURN` (8) only bounds a runaway loop in one Y² turn (per tool instance; one instance per step).
- **Idempotency.** Each send is keyed by Y²'s turn id and a hash of its content, so a replayed step does not start or send twice.
- **Cost.** No polling, no new Durable Object request: the tools read one Postgres metadata row per message/stop and none for start. Y² is woken by the crew as before when a started thread finishes or needs the person.
- **Turn rules.** The three tools count as workspace-neutral in `turn-saving.ts` (like `threads`): Y² has no checkout, and a turn that counted them as changing one would fail on "Y² has no workspace". Y² never commits.
- **Gating.** The tools exist only in Y²'s own turn (`ySquared` in `api-turn.ts`).

## Crew status and wakes

Y² does not read thread transcripts. Each Y project has one `YSquaredCrew` Durable Object (`src/server/edge/y-squared-crew.ts`, named by project id, SQLite, binding `Y_SQUARED_CREWS`, migration v5).

- **Rows.** `crew(session_id pk, title, state, waiting_on, pr_url, last_reply ≤300 chars, updated_at, created_at, last_request ≤200 chars, last_active_at, working_since, start_wake_at)`: one row per thread, rewritten in place (`created_at` = first note, 0 when not recorded; `last_request` = the person's last request, never a wake; `last_active_at` = last turn start/settle note, i.e. when the person or a wake used the thread; `updated_at` keeps its meaning of the last row write). The three columns were added to the deployed table additively: the store checks `pragma_table_info('crew')` at start and `alter table … add column`s the missing ones once; old rows keep working (created "not recorded", last active = their `updated_at`, no request until the thread's next settle note); an identical note writes nothing; rows untouched for 30 days are pruned (at most daily). `working_since` is set by the start note (kept by repeats, cleared on settle). `wake_state` holds `pending`, `pending_due_at`, `last_wake_at`, `last_heartbeat_at`, `wakes_this_hour`, `hour_start`, `alarm_at` (and the wake target); `wake_events` (≤12 rows: what changed since the last wake) and `y2_sent` (Y²'s own sends) are the two small tables added for the wake message. All columns and tables are added additively at start.
- **Push on transitions.** A thread's `ModelConversation.noteTurnStatus` also calls `noteThread` when its turn starts (`working`) and when it settles (`waiting` on the person / `finished` / `failed`), fire and forget under `waitUntil`, errors swallowed. What it waits on, its pull request and last reply come from the transcript copy the chat object already holds (`chatWaitingOn`, `threadHistoryFacts`): no Postgres read. The last request is the last non-wake `userMessage` of that same copy, so it is sent with the settle note (the start note carries none and keeps the stored one): while a thread is still working on a new request, `last request` shows the previous one until it settles. The chat's project, `project.y_enabled` and its Y² id come with the scope `resolveModelConversation` already reads each step (one join, no extra round trip) and are kept in the chat's SQLite (`crew_scope`, written only when they change). A chat of a project without Y, Y² itself and helper chats (any parent: they are not threads) send nothing (`crewProjectFor`; the scope read marks helpers not-Y). The switch is refreshed at the next turn start. The scope is read by the chat (`readChatCrewScope`, `src/server/adapters/crew-facts.ts`), never by the turn's durable-object lease: that lookup found nothing for box turns, so until 2026-11-23 a thread whose turns ran on boxes never reached its crew (production: 1 of 7 recent Y threads ran only on boxes; every new thread's first turn, claimed by a box then handed back, sent its start note with no scope). A settle with no stored scope reads it too. **Titles:** every note carries the thread's title by the sidebar's rule (`sessionTitleFromText` of its first message, `crewNoteFromItems`), the start note too, else the chat's own title, else its request; a start note used to carry none, so a new thread read "Untitled" to Y² until its first turn settled, and for good when that note was lost. Rows stored untitled show their last request's title. **Lost settle notes:** a turn the lease sweep fails (`expireApiTurnLeases`: its object or box stopped) has no executor to tell its chat, so the sweep tells the chat's object (`noteTurnsSettledElsewhere`, registered on the edge with the hub notes), which sends the crew and hub notes as for a box turn.
- **Wake policy** (`crewWakeDelayMs`, `heartbeatDueAt` in `src/domain/y-squared-crew.ts`; `SqliteYSquaredCrew.noteThread` / `takeWake`). A thread TURN settling (`finished`, `waiting` on the person, `failed`; every turn, not only a whole thread done) sets `pending` and a due time `max(now + d, last_wake_at + d)` with d = 5 s for `waiting` / `failed` and 10 s for `finished` (was 15 / 30); a later urgent note pulls an already-set alarm earlier, never later. Plain progress never wakes. Three more things can fire the one alarm: a long-running **heartbeat** (below), and **a thread the person started directly** (below). The alarm sends exactly one Y² turn through the normal send path (a hidden wake message, shown as a silent wake notice) whose text lists what changed since the last wake and who is still working (`crewWakeBody`), then records `last_wake_at`. At most **24** wakes per hour per project (was 12); the 25th stays pending and fires when the hour window rolls over (a held heartbeat is not left pending: the next window re-checks it). A failed enqueue hands the wake back (and keeps its changes) and re-arms the alarm itself: retries after 30 s, 1 min, 2 min, then 5 min, 8 tries in all (`runCrewAlarm`, `src/server/edge/crew-alarm.ts`); after that the next note re-arms it. Y²'s own session id never wakes it.
- **Heartbeat.** While any thread has been `working` (`crew.working_since`) for more than 5 minutes with no wake since (the clock of a thread is `max(working_since, last_wake_at)`), the same project alarm is set for `max(quiet + 5 min, last_heartbeat_at + 10 min)`: at most one heartbeat wake per project per 10 minutes, so again every 10 minutes while threads keep working. No polling and no extra alarm: `rearm` picks the sooner of the pending wake and the heartbeat, only when something is pending or working (a project with nothing working has no alarm; a stale alarm that fires with nothing to do arms nothing). A row `working` for over 6 hours is taken for a lost settle note and gets no more heartbeats. The wake message says which threads are still working and for how long, so Y² can tell how long they have run; a heartbeat with nothing new and no follow-up signal gets no message (see Proactive Y²): since 2026-11-24 the server skips that wake itself (`takeWake` returns `none` and moves the heartbeat clock), instead of paying a model turn for `NOTHING_TO_REPORT` (212 of 389 production wakes in 3 days were that).
- **Direct starts.** When a thread's start note carries a request (`crewRequestFromStartItems`: the last item of the chat copy is a non-wake user message) and Y² did not send it, the person messaged the thread directly: Y² is told at its next wake ("You were not part of this: <thread> got <request>") and, at most once per thread per 10 minutes (`crew.start_wake_at`), woken for it (10 s debounce). Y² marks its own sends first (`noteY2Sent`, one extra crew request per `start_thread` / `message_thread`, a `y2_sent` row valid for 60 minutes, used once), so a thread Y² started or messaged never wakes it (Y² narrates those itself). A start with no request (a wake, an automatic turn) is neither.
- **Reading.** Y²'s `threads` is one `list()` request, `thread` one single-row request. An empty, never-filled crew is filled once from `listSidebarAgentSessions` metadata (no items), then marked reconciled. Without a binding (local development) the tools read that metadata only. Both tools show `last active <relative>`, `created <date>` (or "not recorded"), the last request and the last reply (≤6 short lines per thread in `threads`; order stays needs-the-person, working, then most recently active). `ySquaredInstructions` tells Y² to answer "which thread did X / was last used / created Y" from those, to say plainly what is not recorded (who or which agent built Y² itself, work outside the project's threads, anything older than the crew's records) with a next step (open the most recently active thread or ask it with `message_thread`), and never to mention failures unrelated to the threads.
- **No user MCP servers.** A Y² turn never loads the user's configured MCP servers (`runApiTurn` skips `connectableMcpServers` for Y²) and so never adds the "MCP servers unavailable this turn" notice; on the Claude runner-box route only ytimesy's bridge server is in `mcp.json` (the runner already sets `strictMcpConfig`). `noteThread` accepts the first deploy's older shapes (`turnStatus`, `pullRequest`, `reply`).

Cost per thread-turn (the new columns ride the same upsert): 2 notes (start, settle) = **2 crew requests** (3 when it ends on a card for the person: the waiting hint), ≤2 row writes plus ≤2 `wake_state` / `wake_events` writes. A wake adds 1 alarm invocation, ≤3 `wake_state` writes, one normal Y² turn (model cost: API tokens, or the person's plan usage on the Claude runner) and its `threads` read (1 request). A Y² `start_thread` / `message_thread` adds 1 mark request. A Y² overview read is 1 request, 0 writes.

## Staying in the loop

The owner's feedback: Y² reported only once a thread was done. What keeps the person in the loop now, and what each part costs.

- **Live status card** (`src/features/workspace/y-squared-card.tsx`, data in `src/domain/y-squared-card.ts`): pinned at the top of the Y² chat; "Waiting on you / In progress / Done recently" with status icon, title, a **client-side elapsed clock** (`elapsedClock` from `workingSince`, ticking once a second only while something works), the person's last request (≤120 chars), what it waits on and a PR link; needs-you first. **No model call, no timer-driven request.** Its rows are the sidebar's chat list (`['agent-sessions', projectId]`), which the user's hub already refreshes when a chat's turn changes; the crew's last request / PR come from one `readYSquaredCrewCard` request (one DO `list()`) per change of the rows' status signature (`cardSignature`), never on a clock. The crew read can lag the row by one note when both change together (it then shows the previous request until the next change).
- **Narration at meaningful moments only** (the wake policy above): turn finished / needs the person / failed (5 s, 10 s debounce), a long-running heartbeat, a thread the person started directly. `ySquaredInstructions` makes each wake a short delta, a one-line acknowledgement when Y² starts or steers threads, terse replies to terse commands, and a pointer to the card instead of repeating it.
- **`message_thread` modes**: `queue` (default: a waiting row, `released: false`, that starts the thread's next turn when the running one ends; several wait in order, at most 50 per chat), `steer` (a running thread: the same row stored already `released: true`, the mark Send puts on a person's queued message, so the thread takes it at its next model step with no extra turn; a Claude Code run takes released rows only after its next tool call, and a turn on a runner box may see it up to 10 s late, docs/turn-runner-boxes.md; if the turn ends first the row starts the next turn; an idle thread starts a turn as for any send), `interrupt` (stops the running turn through `stopTurnKeepingQueue`, then sends). The old text said `steer` was `queue`; that was wrong for root chats.

Estimated DO requests (per project, not counting the threads' own objects or the user hub): a busy hour with 10 thread-turns is 20 notes + ≤10 wakes × 2 (alarm + `threads`) + ≤6 heartbeats × 2 = **≈50 requests/hour**; the ceiling is 24 wakes × 2 + 20 notes + ≤10 marks ≈ **80/hour**; an idle project costs 0 (no alarm, no polling). Opening the Y² chat adds 1 request per status change (≈ one per thread-turn edge). Against ~10k DO requests per user per month (`docs/cloudflare-budget.md`) that is ≈12 hours of continuous heavy work at the ceiling, ≈25 at the busy-hour estimate. Plan usage: each wake is one short Y² turn; at most 24 per hour per project, of which at most 6 are heartbeats, 2 per thread-turn is the typical case. Wake rate is the dial: lower `CREW_WAKES_PER_HOUR` or raise `CREW_HEARTBEAT_EVERY_MS`.

## Proactive Y²

Y² acts without being prompted and escalates only real blockers (the Devin Bots / Capy Captain shape), so the person can mostly talk to Y² alone. Code: `src/domain/y-squared-proactive.ts` (pure), the store/alarm (`y-squared-crew-store.ts`, `crew-alarm.ts`), the `schedule` tool (`y-squared-tools.ts`), settings (`y-mode-settings.tsx`). No new alarm and no polling: the crew keeps its ONE alarm slot, and `rearm` sets it to the earliest of the pending wake, the heartbeat, the next active schedule and the next stall signal. All state is in the crew's SQLite (additive columns/tables); no Supabase read is added.

**1. Stall / follow-up signals** (setting `stall_nudges`, default ON, in `wake_state`). They ride the wake body (`proactiveWakeLines`), at most once each:
- *Stuck*: a working thread whose turn has shown **no real progress** for `max(20 min, 3 × its usual turn)`, or 60 min with no history. When that clock runs out the alarm first reads the turn itself (`readThreadProgress`, one Postgres read, only then): the newest of the running turn's last write (a checkpoint after each model call and tool result, or a progress write; Durable Object or box alike) and its last lease renewal (a box renews every 10-30 s through a long tool call or a Claude run). That moves the clock (`crew.progress_at`, `stallClockFrom`), so a live turn is checked again one window later and never called stuck; a queued turn is not stuck either; a thread with no queued or running turn lost its settle note and its row settles now (finished, or failed as the chat says), so Y² hears that instead. The signal says how long the turn was quiet. Before 2026-11-23 the clock ran from the start note alone: of 17 "may be stuck" signals in production, the 13 that match a turn running at the time all completed normally. The usual turn is a moving average (`typical_work_ms`, 0.7/0.3) of that thread's `working_since → settle` durations, learned at each settle note; a run is nudged once (`stall_nudged_for = working_since`); a row working over 6 h is a lost settle note and is never nudged (the progress check settles it when it runs). Cost: one Postgres read per due check, at most one per working thread per stall window.
- *Waiting on the person*: a `waiting`/`failed` thread gets a reminder after 30 min, then at most every 3 h, at most 3 per wait (`reminded_at`, `remind_n`, reset by any new note for the thread).
- *Skipped for lack of data*: **a finished thread's pull request failing CI or sitting unmerged for N hours**. The crew rows hold only the PR URL (`pr_url`) taken from the transcript, never its CI or merge state, and checking it would need a GitHub read per project on a timer (polling) or a webhook into the crew, neither of which exists. Y²'s instructions say so, and to report it only when a thread's own reply says so. A webhook-to-crew note would be the way to add it later.
Y² decides: steer or stop the stuck thread, answer a routine waiting one itself, ask the person only for a real blocker.

**2. Scheduled check-ins.** Tool `schedule` (`action` create | list | cancel). Specs: one time (`inMinutes`, or `at` = local `YYYY-MM-DDTHH:MM`), daily/weekday (`time` + `days`, 0 = Sunday), repeating (`everyMinutes` ≥ 30). Table `schedules(id, prompt, spec, tz, status, next_due_at, last_run_at, created_at)`, at most **10 active** per project; done, cancelled and missed rows are kept 7 days then pruned. A due schedule rides the same wake (`runCrewAlarm` → `enqueueWake`) with the saved prompt in the body; it is consumed only once the wake was enqueued (`wakeSent`); a failed send holds schedules and signals until the retry (`proactive_hold_until`), gives the cap slot back, and never loops. *Missed*: a one-time check-in overdue by more than 6 h is dropped (`missed`, no wake); a repeating one that is late fires once and continues from now (missed occurrences are not replayed). *Cap*: schedules, stall nudges and reminders count against a separate **48 per rolling 24 h** (`proactive_today`), not the 24/h of event wakes; over the cap they are skipped for the day and not replayed. If a proactive item is due together with a pending wake or heartbeat it goes in the same message. *Time zone*: schedules store an IANA zone; the saved one is the browser's (`Intl.DateTimeFormat().resolvedOptions().timeZone`), written once, the first time Project settings → Y is opened with Y on; the tool can take an explicit `timezone`; with none saved, UTC is used and the tool result tells Y² to say so. DST is handled by walking calendar days in UTC and converting each local time (`zonedTimeToUtc`). The crew learns Y²'s chat/user when a schedule is created, so a schedule works even before a thread note.

**3. Escalation policy and quiet wakes** (`ySquaredInstructions`): handle routine things itself (re-send a transient failure, steer a stuck thread, start a follow-up the person approved) and say what it did in one line; escalate only blockers or irreversible/costly decisions (merge, deploy, delete, spend) with a one-line ask and a recommendation; never repeat a reminder; end each proactive wake with a concrete ask, a one-line result, or silence. *Silence*: a turn must end with text (an empty reply throws `missing-final-result` in `api-turn.ts` and retries/fails the turn), so a wake with nothing to say replies exactly `NOTHING_TO_REPORT`. `childTaskPublicItems` drops that agent message, so the Y² chat shows no bubble (the wake turn itself already shows only a silent notice); it still costs the model turn (cheap: the wake text says when no tool call is needed). The heartbeat's old "one brief still-working line" is replaced by this.

**4. Settings UI** (Project settings → Y, only with Y on; `YProactiveView`): a switch for stall nudges, "proactive wakes today: n of 48", the time zone in use, and the active schedules with Cancel (server fns `readYProactiveFn`, `saveYProactiveFn`, `cancelYScheduleFn` → crew `proactive`, `saveSettings`, `cancelSchedule`; one crew request each, loaded only when the section is open, never on a timer).

Cost: no new alarms or timers. A schedule adds 0 requests until due; a due one adds the usual wake (1 alarm invocation, 1 `threads` read, one Y² turn). The proactive daily cap bounds the extra Y² turns to 48/day/project on top of the ≤24/h event wakes; turn `schedule` calls add 1 crew request each.

## Canvases in the Super agent chat

The person talks to Y² only, so a thread's canvas (the `canvas` tool: items of kind `canvas`, `{title, revision, html|null, path?}`) must be readable, visible and iterable there.

**Before:** the `thread` tool listed `"Thread art" (revision 1)` (titles and revision numbers; `threadOutcomeForOwner` read canvases without html). Y² could not say what a canvas contained, and the person had to open the thread to see or annotate it.

**After**

- `thread` lists, per canvas title, the LATEST revision (highest number, the rule of `savedCanvasRevision`), its size in KB, whether it has images and a description of at most 300 characters (`canvasDescription`: title, headings, visible text; scripts, styles and data: URIs removed; image alt text counted). One query by chat id: size and the images flag are computed over the whole document in SQL, the description from the first 24,000 characters after base64 `data:` URIs are cut out in SQL (`CANVAS_DESCRIBE_CHARS`); at most 6 canvases.
- `read_canvas {id, title, part?}`: the latest revision as a text outline (`canvasOutline`: `#` headings, paragraphs, `- ` items, table rows as `a | b`, `[image: alt]`, `[svg: title]`), at most 12,000 characters per call, `part` pages through a longer one; names the revision, size and part count. Never html or base64. One item read (`latestCanvasForOwner`, same `agent_session_item` row shape as the lazy whole-item read), only when called.
- `show_canvas {id, title}`: reads the same one item and returns a `shown` result with `ownerThreadId` and `ownerItemId`; `applyApiProgress` turns it into a canvas card in Y²'s own transcript like the `canvas` tool's (`isCanvasDisplayTool`), keeping the thread's revision number and title, so the stepper, side-by-side compare, pins and the budget (`withBoundedCanvasHistory`, `CANVAS_CHAT_BUDGET`) work in the Y² chat. The model reads only a one-line confirmation (`toModelOutput`). Over `CANVAS_HTML_LIMIT`, an unknown thread (other project, Y² itself, subagents) or canvas gives a clear message; if the newest revision lost its html to the thread's budget, the newest revision that still has html is used and the result says so. A revision already shown from that thread in this turn is not added twice.
- All three tools are in `Y_SQUARED_TOOLS` and `turn-saving`'s read-only set, and ride `ySquaredTools` on every route (API/Codex/Grok directly; Claude Code through the runner box bridge, which serves every tool of the set and honours `toModelOutput`).

**Loop** (feedback in the Y² chat → thread → new revision in the Y² chat)

1. The person pins notes on the canvas card in the Y² chat; the inspector composes `Canvas feedback on "<title>" (revision N) [thread:<id>], k notes:` (`canvasFeedbackMessage` with `ownerThreadId`; `canvasFeedbackOwner` reads the marker back).
2. Y² (instructions) sends it to THAT thread with `message_thread`: `steer` if the thread is working, else the default (an idle thread starts). It forwards the notes verbatim with selectors, the title and revision, and asks for the next revision with the SAME title; it says so in one line and ends its turn.
3. The thread revises and shows the canvas again (next revision number, same title).
4. The thread's settle note carries `showed canvas "Thread art" (revision 2)` (`crewCanvasLine`, from the items the chat object holds: titles and revisions, no database read, no html). It rides the wake event's detail; it is not stored in the crew rows. A turn that showed a canvas is news even if its reply text did not change.
5. Y² wakes, calls `show_canvas` again: revision 2 appears in the Y² chat next to revision 1 (compare works), and it tells the person the change in one or two lines.

**Egress** (Supabase): wake body: titles and revision only, about 45 bytes per canvas (≤ 200 bytes per thread, ≤ 3 canvases named). `thread`: ≤ 6 canvases × (≤ 24,000 characters read from the database for the description, ≤ 300 sent to the model, plus a line of facts) → ≤ ~144 KB read in the worst case and ~2 KB to the model; typical canvases (a few KB of visible markup) read far less. `read_canvas`: one item (≤ 500,000 characters read), ≤ 12,000 characters returned per call. `show_canvas`: one item read (≤ 500,000 characters) and written once into Y²'s transcript (Y²'s page reads omit html and read it lazily when the card is opened, as for any canvas); the model reads about 200 characters. `threads` carries no canvas information.

Not done: two threads that show canvases with the same title collide in Y²'s chat (a canvas is identified by title); a note on an older revision in the Y² chat is still sent as feedback on that revision and the thread decides.
